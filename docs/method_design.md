# 新方法的設計：為什麼拿掉中間的 barrier 還能保證正確

> 對應程式：`exp/M17_epoch_ab/fused_ar_norm_nf.cu`（正式版，fp16／bf16，TP=8）。
> 本文件說明「做了什麼、為什麼這樣做是對的、哪些是證明、哪些只是觀察」。
> 數字出處見各實驗卡；本文件不引入新數據。

## 白話結論

1. **拿掉的是「中間的互相等齊」，不是全部。** 開頭的互相等齊（start barrier）還在，因為每張卡要確定別人的輸入準備好了才能去拿。拿掉的是「加總完、要收齊之前」那一次。
2. **取代它的是「資料自帶記號」。** 每張卡把算好的結果主動送給另外 7 張，資料裡每 128 byte 夾一個 8 byte 的記號（本次呼叫的編號）。收的一方看到記號等於目前的編號，就知道這份資料是新的、可以用。不用等所有人都做完。
3. **還要回答另一個問題：舊資料會不會被蓋掉、或被誤認為新資料？** 靠三件事：記號帶著呼叫編號（舊資料編號不對，不會被接受）、一張卡要等收齊 7 張卡的資料才結束（所以結束時，別人一定已經讀完它的輸入）、開頭那次互相等齊（保證下一次呼叫不會比別人早動手）。
4. **哪些是證明、哪些只是觀察**：上面第 3 點的推理是邏輯論證；但「128 byte 一起送達，看到記號時資料一定也到了」是硬體行為的假設（NCCL 的 LL128 也依賴它），我們只觀察到 0 次違反，沒有證明，也還沒做壓力測試。
5. **這個設計是一步一步量出來的**，不是一開始就設想好的（見「設計怎麼來的」）。

## 1. 一次呼叫做什麼（程式流程）

每張 GPU 上同一個 kernel：

| 步驟 | 內容 | 同步方式 |
|---|---|---|
| ① 起點 barrier | 每個 block 對每個 peer 寫自己的旗標（值＝本次編號 epoch），再等 peer 的旗標等於 epoch | 旗標，**保留** |
| ② 分工加總（pull） | 這張卡負責的每一列（token），從 8 張卡的輸入各讀 16 byte 一單位，相加，再加 residual | 直接讀對方記憶體，不需同步（①已保證對方輸入就緒） |
| ③ 正規化 | 同一個 block 內算平方和、乘 rstd 與 gamma，寫入本地輸出 | block 內同步 |
| ④ 送出（push） | 把正規化後的那一列，以 LL128 格式寫進另外 7 張卡的「接收區」 | 寫入；每 128 byte 含 8 byte 記號 |
| ⑤ 接收 | 輪詢自己的接收區，每個 128 byte 的記號等於本次 epoch 才接受，複製到輸出 | 輪詢記號，**取代中間 barrier** |
| ⑥ 收尾 | 最後完成的 block 把全域 epoch 加一，供下一次呼叫使用 | 完成計數（atomicAdd），無 fence |

和 vLLM two-shot 的差別：vLLM 在加總與收齊之間有一次全體 barrier，收齊用 pull；正規化是另一個 kernel。

## 2. LL128 格式（記號怎麼夾進資料）

- 一個 128 byte 單位 ＝ 16 個 u64：**15 個放資料，1 個放記號（epoch）**。
- 一個 warp 的 32 個執行緒負責 4 個這樣的單位；每個執行緒用一條 `st.volatile.global.v2.u64`（16 byte）寫出。每 8 個執行緒組成一個單位，第 8 個執行緒（`part==7`）的第二個 u64 是記號。
- 接收端每個執行緒用一條 16 byte 讀取；整個 warp 用 `__all_sync` 確認每個單位的記號都等於 epoch，才接受這批資料。
- **假設 A（未證明）**：同一個 128 byte 單位的資料與記號一起送達（看到記號時，同單位的 15 個 u64 也已是新的）。這是 NCCL LL128 協定所依賴的行為，不是 NVIDIA 文件的保證。

## 3. 為什麼可以不要中間 barrier：三個要回答的問題

### Q1　收的一方怎麼知道資料已經到了？

看記號。記號等於本次 epoch ⇒ 這個 128 byte 單位是本次呼叫送來的。（依賴假設 A）

### Q2　送資料的一方會不會把別人還在讀的東西蓋掉？

分兩種緩衝區：

- **輸入 x**：下一次呼叫的前一層運算會覆寫它。要求：覆寫時沒有任何 peer 還在從這份 x 拉資料。
  論證：某張卡 A 要結束，必須先收齊所有擁有列的 peer 送來的每一列；每個 peer 送某一列之前，已經把這一列從所有卡（包含 A）的 x 讀完。因此 A 結束時，所有 peer 都已讀完 A 的 x，A 的下一層可以放心覆寫。（沒有擁有列的 peer 不讀 x，也不送資料，不影響。）
- **接收區**：peer 的下一次呼叫會寫入。接收區分兩份，依 epoch 單雙數輪流使用。論證：peer 要寫第 e+2 次的接收區，必須先通過第 e+2 次的起點 barrier，那要求 A 已經開始第 e+2 次、也就是結束了第 e 次。
  - *附註（推測，未驗證）*：由同樣的論證，起點 barrier 本身可能已足以防止 e+1 次的覆寫，雙份可能是多餘的保險。

### Q3　上一次呼叫留下的舊資料，會不會被誤認為這一次的？

不會。記號是 epoch，每次呼叫加一；舊資料的記號是舊 epoch，不等於本次的值，接收端不接受。

**M16 發現並修好的漏洞**：舊版每個 block 各自計數 epoch，若不同大小的呼叫（不同 block 數）交錯執行（例如每個批次大小各錄一個 CUDA graph），各 block 的計數不一致，起點 barrier 就卡死。修法：全域 epoch（`ctr[0]`），所有 block 讀同一個值；最後完成的 block 才把它加一（`ctr[1]` 計完成數）。M17 再拿掉修法中多加的兩個 `__threadfence()`：理由是每個 block 在 kernel 開頭就讀了 epoch 並用在起點 barrier，而下一次呼叫要等本 kernel 結束（同一 stream 的順序）。

## 4. 哪些是證明、哪些是觀察

| 項目 | 性質 | 證據／缺口 |
|---|---|---|
| Q2 的覆寫論證（輸入、接收區） | 邏輯論證（依賴 stream 順序、每張卡收齊所有送來的列） | 沒有形式化；只有測試 |
| Q3 的 epoch 區分舊新 | 邏輯論證＋測試 | 交錯測試 120/120（M16、M17） |
| 假設 A：128 byte 同時可見 | **硬體行為假設** | M12／M13 探針 0 次違反；**無壓力測試**（稽核阻擋項，D040） |
| 無 `__threadfence()` | 論證＋觀察 | M17 前後比較、交錯測試；**未在高負載下測** |
| 結果數值正確 | 測試 | 與 fp32 參考比，相對誤差 ≤ 2⁻⁵（含 residual）；fp16／bf16、hidden 5120／8192 |
| 起點 barrier 的 32 位元旗標 | 限制 | epoch 以 32 位元比較，約 43 億次呼叫後環繞；尚未處理 |

## 5. 設計怎麼來的（每一步的量測依據）

1. **M5、M11**：量到通訊占每步 8–27%；vLLM 的兩次 barrier 占 kernel 內 34–42%，每次之間還有 3–4 µs 空檔，連線只用到 10–31% → 問題在同步，不是頻寬。
2. **M8、M11**：想用跨卡原子加法做分工加總，正確但慢（一次只能送 4 byte；bf16 在 A100 靠 CAS 模擬）→ 放棄。
3. **M12、M13**：改用 16 byte 的 LL128 寫入。
   - 收齊（all-gather）：主動送＋記號 ≈ 自己去拿，且不用中間 barrier（80–320 KB：4.0–4.5 µs，對 vLLM 的「等待＋收齊」12.2–12.4 µs）。
   - 分工加總（reduce-scatter）：主動送慢 1.3–1.8 倍 → 維持自己去拿。
   - 因此結構是「**pull 加總、push 收齊**」。
   - 大資料時 M12 看到的「變慢」是測試程式問題（每次清空、單次執行），M13 改連續執行後消失。
4. **M14**：把加總、正規化、push 收齊接成單一 kernel；正規化只做自己的列（residual 分片，同 LMDeploy）。
5. **M15**：模板化支援 bf16。
6. **M16、M17**：發現 epoch 漏洞並修好；去掉多餘的 fence。
7. **M18、M19**：校準量測方式（時脈、暖機）；診斷小批次較慢的原因。

## 6. 與既有做法的關係（避免誤稱新意）

- LL128（每 128 byte 夾旗標）：NCCL 既有協定。
- 帶記號的 push（Lamport 式）：TRT-LLM 已有。
- 分工加總→正規化→收齊：LMDeploy、TokenWeave 已有。
- 同期工作 flash-comm（arXiv 2611.06634）：資料塊自帶到齊證據、去掉前後 barrier，機制相近；平台 B300、未併入 RMSNorm。**新意待精讀後確認**（D046）。

## 7. 待做（與可信度直接相關）

1. 壓力測試：GPU 同時跑矩陣乘法、長時間連續呼叫、不同大小交錯，檢查任何錯誤（針對假設 A 與無 fence）。
2. 把 Q2 的論證寫成更嚴謹的形式，或用「故意延遲某張卡」的測試去逼出覆寫問題。
3. 驗證接收區雙份是否必要（附註）。
4. 放進真實的 vLLM，確認輸出與原本一致（residual 分片的語意，U6）。
