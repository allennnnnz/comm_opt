# 全面盤點與下一步策略（2026-11-04）

> 使用者要求（M18 步驟 b 之後）：「暫停所有事，重新盤點當前的狀態，好好整理並做出下一步的策略」。
> 本文件納入使用者以 Copilot 做的稽核（commit `993afd5`、D040）。所有數字都可追到 `exp/<ID>/README.md` 與 `results/`。

## 一頁摘要

1. **研究走到哪**：主線是「8 張 A100、生成階段的 all-reduce＋residual＋RMSNorm」。原型已經做出來，結果正確，而且在單獨的測試程式中比 vLLM 快；但還沒放進真實推論，也還沒過「確認題目」（G2）這一關。
2. **扎實的部分**：通訊佔生成時間 8–27%；vLLM 的時間有三分之一花在全體等待、每次之間還有 3–4 µs 空檔，連線只用到 10–31%；原型在 16／32／64／128 tokens 比 vLLM 快 1.23／1.70／1.39／1.38 倍（最高時脈、同一次量測、5 次 launch）。
3. **還不夠的部分**：1–4 tokens 時原型比 vLLM 慢；16 tokens 只快 1.23 倍；端到端效益沒量過；「到齊記號」與「去掉等待步驟」的正確性只有觀察沒有壓力測試；「可達水準」的定義有問題；比較對象只有 vLLM 預設；只有 TP=8、一台機器。
4. **最大的風險**：端到端效益可能只有幾個百分點；原型的每個零件都有前例，新意要靠「在沒有交換器加總的 GPU 上，時間花在哪、該怎麼組合」的分析來撐；A100 是上一代硬體。
5. **建議策略**：先用 1–2 天補地基（壓力測試、最強對照組、重新定義可達水準、實際使用情境調查）並修掉小訊息變慢；接著把原型放進 vLLM 量端到端，**用端到端結果決定題目定位**（系統論文或分析論文），再過 G2。

### 2.2 有條件或未驗證

| # | 項目 | 為什麼不夠 |
|---|---|---|
| U1 | 端到端效益（粗估 3–10%） | 只量了單獨的 kernel；真實推論中前後有 GEMM、快取與 SM 被佔用 |
| U2 | 「到齊記號」（LL128 128 byte 一起送達）與「不用 fence」的正確性 | 只有「測試中 0 次違反」的觀察；沒有在 GPU 同時做大量計算時壓力測試；記憶體順序的論證是非正式的 |
| U3 | 「可達水準」 | M6 的定義 = 最小資料時最快的延遲（one-shot 類）＋ two-shot 的資料量 ÷ 最高頻寬，兩者拼湊，未必做得到；在較低時脈量的；沒有包含 RMSNorm |
| U4 | 比較公平性 | 對照組只有 vLLM 預設（以及 TRT-LLM、LMDeploy 合併版）；M7 找到的「每個大小調到最好的現成做法」＋RMSNorm 還沒比；M14–M17 的「最佳 block 數」是事後挑選（步驟 b 已確認影響很小） |
| U5 | 推廣性 | 只有 TP=8、一台機器、hidden 5120／8192；實際服務可能是 TP=4、讀入與生成混在同一批（chunked prefill） |
| U6 | residual 分片的語意 | 只在單一 kernel 層級驗證；沒有在真實模型裡確認輸出一致 |

### 2.3 被推翻或更正的

| 原本的想法 | 結果 |
|---|---|
| 用跨卡原子加法做分工加總 | 正確但比 vLLM 慢（M11）；問題在一次只能送 4 byte |
| 缺 cluster 是合併變慢的主因 | 不是主因（M10） |
| 修漏洞讓原型變慢 9–25% | 主要是機器狀態；同一次量測只差 0.3–3.5%（M17） |

## 4. 方法上學到的事

1. **時脈要固定**：不暖機時越早量的越慢；之後一律先暖機 2 秒（步驟 a）
2. **每次量測的第一個設定要丟掉**（步驟 a）
3. **跨次量測不能直接比**：同一份程式在不同次量測可以差 10% 以上（M15 vs M16）；比較一律在同一次量測內交錯
4. **挑參數要先校準、再驗證**：事後從多個選項挑最好的會高估（步驟 b 驗證後效果消失）
5. **測試程式本身也會出錯**：暖機迴圈的全體通訊對不上（步驟 a 第一次）、單次執行加清空緩衝區讓大資料看起來變慢（M12 → M13）；量測前都要先小試跑

## 5. 研究定位的風險

| 風險 | 說明 | 可能的對策 |
|---|---|---|
| 新意 | LL128（NCCL）、帶記號的 push（TRT-LLM Lamport）、分工加總→正規化→收齊（LMDeploy、TokenWeave）都有前例 | 把貢獻放在「沒有交換器加總的 GPU 上，生成階段 all-reduce 的時間花在哪」的量化分析，以及由此推出的「reduce-scatter 用 pull、all-gather 用 push」的不對稱設計；或擴大到與前後 GEMM 合併 |
| 效益大小 | 端到端可能只有幾個百分點 | 先量端到端；找延遲敏感的情境（例如每個字的延遲有上限的線上服務） |
| 硬體代表性 | A100 是上一代；新一代有 NVLS | 論證「沒有交換器加總的平台」仍普遍（A100／A800、L40S、PCIe 版、部分 AMD）；至少用文獻與規格支持 |
| 小訊息變慢 | 1–4 tokens 比 vLLM 慢，真實服務常有小批次 | 小訊息改用 one-shot（原改善 2） |

## 6. 策略選項

| 選項 | 做什麼 | 投入 | 風險 | 得到什麼 |
|---|---|---|---|---|
| **A 端到端優先** | 把原型放進 vLLM（含小訊息 one-shot 路徑），量 Qwen2.5-32B／70B 等級、TP=8 的每個字延遲 | 3–5 天 | 整合工作量（residual 分片、輸入要放在共享記憶體、多個 CUDA graph） | 最快知道「這件事在真實推論中值不值得」 |
| **B 地基優先** | 壓力測試、最強對照組、重新定義可達水準、實際使用情境調查（不需 GPU 的部分） | 1–2 天 | 低 | 讓目前的結論經得起審查；不會產生新的加速 |
| **C 擴大貢獻** | 把 all-reduce 和前一個 GEMM 合併（FLUX 式），一起去掉 start barrier 與空檔 | 1–2 週 | 高（要改 GEMM） | 可能明顯更大的加速與新意 |
| **D 轉分析型論文** | 以量化分析為主，原型當示範 | 1 週左右可成稿 | 低 | 新意與影響力較低 |

### 建議：B（精簡版）＋修小訊息 → A → 依結果決定 C 或 D

1. **第一段（約 2 天，B 精簡版＋改善 2）**
   - 壓力測試：原型在 GPU 同時跑矩陣乘法時，長時間交錯呼叫，檢查有沒有任何錯誤（回應稽核 U2）
   - 最強對照組：M7 的「每個大小最好的現成做法」＋RMSNorm，與原型在同一次量測比較（U4）
   - 重新定義可達水準：分開報「延遲下限」與「頻寬下限」，用 1410 MHz 重量（U3）
   - 實際使用情境調查（不需 GPU）：常見 TP 數、生成批次大小分布、讀入與生成是否混批（U5）
   - 小訊息改用 one-shot，讓 1–8 tokens 至少不比 vLLM 慢（M18 步驟 c）
2. **第二段（約 3–5 天，A）**：放進 vLLM，量端到端每個字延遲與吞吐，並確認模型輸出一致（U1、U6）
3. **決策點（G2）**：
   - 端到端在常見批次有明顯改善（例如 ≥ 5%）→ 系統論文路線，考慮 C 當加分項
   - 改善很小 → D 分析型論文，原型當示範
4. **暫緩**：M18 步驟 d（拿掉 start barrier）、e（大訊息）——要等端到端確認值得再做

## 7. 需要使用者決定的事

1. 採用哪個策略（建議：B 精簡版＋小訊息修正 → A → 依結果決定）
2. 第一段的項目與順序是否同意
3. 端到端「明顯改善」的門檻（建議 ≥ 5% 每個字延遲，在批次 16–64）
4. 是否要先補一次主線的正式 G1（把 M6–M13 的現象整理成清單）
