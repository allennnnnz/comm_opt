# 目前為止的研究脈絡（2026-11-04，M0–M11）

> 給使用者規劃新做法與之後實驗流程用。每個數字都可以追到 `exp/<ID>/README.md` 與 `results/`。
> 「事實」= 重複量測過；「推論」= 有數據支持但沒直接驗證；「未知」= 還沒量。

## 一、一頁摘要

1. **問題值得做。** 推論生成文字時，8 張卡每一層都要「加總同步」兩次，每次 80 KB–1.3 MB。它占生成階段每一步的 8–27%（M5）。現有最快的做法比這台機器做得到的水準慢 1.5–2.1 倍（M6）。估計做到可達水準，整體生成可快約 6–14%（M6）。
2. **慢不是因為路不夠寬。** 加總時，8 張卡之間的連線只用到 10–31%（M11）。時間大約是：**一半在搬資料**（而且只發揮該有速度的 25–65%）、**三分之一在互相等待**、**六分之一是兩次加總之間的空檔**（每次 3–4 微秒）（M11）。
3. **現有的改進方法在 A100 上都沒用。** 挑對設定只能補一部分（M7）。TensorRT-LLM、LMDeploy 的「加總＋正規化合併」在 A100 上沒有比 vLLM 的「分開做」快（M9），因為它們是為新一代 GPU 設計的，搬資料的方式在 A100 上吃虧（M10）。
4. **A100 少了五個新一代 GPU 的功能**，每一個都對應一個現有做法在 A100 上失效的原因（見第三節）。
5. **我們新做法的地基「一半成立」**：跨卡原子加法在 A100 上正確（計數器到齊時資料一定加完，M8、M11）。但用它一次推 4 byte，比 vLLM 一次讀 16 byte 慢（M11）。設計要調整。

## 二、故事線

```
大範圍量測（M0、M4、M2）
  └─ 找到 NCCL 一對一傳輸的通道問題（F1）→ 擱置，見第七節
量端到端通訊佔比（M5）
  └─ 推論生成階段的加總同步：佔每步 8–27%，而且小資料離硬體上限很遠
比較現有做法（M6）→ 找慢在哪（M7）
  └─ 挑對設定只補一部分；「一次全送」和「分兩次傳」各有補不掉的缺點
確認新論文的做法能不能搬到 A100（M8）
  └─ 「資料自己帶到齊記號」的原子加法在 A100 上成立
查文獻與框架（D018）
  └─ 「加總＋正規化合併」別人已經做了，但在 A100 上沒人做好
量別人的合併做法（M9）→ 找原因（M10）
  └─ 在 A100 上沒變快；缺 cluster 只解釋一部分，主要是搬資料方式不適合 A100
動手前的最後檢查（M11）
  └─ 路沒塞滿；時間花在等待和空檔；4-byte 原子推送比 vLLM 慢 → 設計要調整
```

## 三、A100 少了什麼功能，造成什麼後果

| 新一代 GPU 才有的功能 | 誰依賴它 | 在 A100 上的後果 | 證據 |
|---|---|---|---|
| 交換器內加總（NVLS／multimem） | NCCL 新做法、TokenWeave、LMDeploy 合併的快速版 | 只能走「8 張卡互相等兩次」的慢版本 | 讀程式（D018、M10） |
| 多個運算單元合作處理同一列（cluster） | TensorRT-LLM 合併 | 一列只能給一個運算單元：大模型（寬 ≥ 6400）無法啟動；小訊息只動用 2–16 個運算單元 | M9、M10（事實） |
| 讓下一步提前開始（PDL） | TensorRT-LLM、FlashInfer | 每次加總之間的 3–4 µs 空檔藏不掉（新 GPU 能藏多少未驗證） | M11（空檔是事實，能藏多少是推論） |
| 一次 16 byte 的向量原子加法 | 《Every µs Matters》 | 原子加法每個執行緒一次只能 4 byte | M8（編譯失敗）、M11 |
| bf16 原子加法 | — | 用重試迴圈模擬，會出錯（347,886 次違反） | M11（事實） |

## 四、每個實驗：問了什麼、得到什麼

| 實驗 | 問題 | 主要發現 | 對研究的意義 |
|---|---|---|---|
| M0、M4 | 這台機器的通訊特性 | 大資料能用到 NVLink 的七成多；8 卡一對一傳中等資料只有 2 卡的 36–41%（F1）；8 張卡對稱 | 機器健康；F1 是一個獨立的研究點 |
| M2 | F1 的原因 | NCCL 依「GPU 總數」而不是「實際傳輸對象」分配通道；模型預測 143/143 點正確；改設定只能部分修好 | F1 已擱置 |
| M5 | 通訊占端到端多少 | 推論生成 8–27%、讀入 24–30%；訓練 11–22%；通訊和計算同時跑會讓計算慢約兩成 | 選定「生成階段的加總同步」為主線 |
| M6 | 現有做法離上限多遠 | 64 KB–1 MB 最快的現成做法慢 1.5–2.1 倍；沒有一種做法在所有大小都最快；NCCL 預設慢 2–4 倍 | 值得做 |
| M7 | 慢在哪 | NCCL 選錯運算單元數（慢 1.35–2.33 倍）；但每個大小都挑最好的設定，仍慢 1.44–1.91 倍 | 光挑設定不夠，要新做法 |
| M8 | 「資料自己帶到齊記號」的原子加法在 A100 上成立嗎 | 7 對 1、3×2^20 行，0 次違反；匯入總頻寬 235–241 GB/s；沒有 16 byte 向量原子加法 | 可以搬到 A100，但只做搬移的貢獻偏弱 |
| 文獻（D018） | 合併正規化有人做過嗎 | TensorRT-LLM、LMDeploy 有 A100 可走的合併；vLLM、SGLang 在 A100 上不開 | 合併本身不是新貢獻 |
| M9 | 別人的合併在 A100 上多快 | 沒有比 vLLM 分開做快；TensorRT-LLM 分兩次傳的版本慢 2 倍；最好的做法仍比上限慢 1.8–3.1 倍 | 空間很大，而且 A100 上沒有好的合併做法 |
| M10 | 為什麼合併沒變快 | 多派 4 倍運算單元只讓分兩次傳的版本快 1.3–1.6 倍；缺 cluster 不是主因，但造成大模型無法啟動 | 要省時間得同時拿掉等待、少搬資料 |
| M11 | 新做法的地基、時間花在哪、路有沒有塞滿 | 見下一節 | 設計要調整 |

## 五、M11 的時間預算：vLLM 一次加總花在哪

以 320 KB（約 32 句話）為例，vLLM 用「分兩次傳」，每次 **21.1 µs**：

| 部分 | 時間 | 說明 |
|---|---|---|
| 起點等待 | 2.1 µs | 8 張卡互相確認「都到了」 |
| 第一階段：分工加總 | 2.8 µs | 每張卡讀 8 份中自己負責的那 1/8 相加 |
| 中間等待 | 4.8 µs | 確認大家都加完 |
| 第二階段：收齊 | 7.6 µs | 從 8 張卡收回加總結果；**只有 1/8 的執行緒在做事**，所以很慢 |
| 兩次之間的空檔 | 3.7 µs | 啟動、運算單元起跑不齊等 |
| **合計** | **21.1 µs** | 可達水準 7.9 µs；理想搬資料時間只要約 2.5 µs |

其他大小的比例差不多：搬資料約 47–55%、等待約 29–33%、空檔約 16–23%。另外，vLLM 正規化是另一個獨立步驟，每次約 4.5–6 µs（M10，數量級）。

**每一塊可以用什麼方法縮短（推論，尚未驗證）：**

| 部分 | 可能的方法 | 已知的證據 |
|---|---|---|
| 空檔 3–4 µs、獨立的正規化約 5 µs | 把加總和正規化放進同一個步驟（甚至連續幾層一起） | M11 量到空檔；M10 量到正規化步驟 |
| 中間等待約 5 µs、起點等待約 2 µs | 讓資料自己帶「到齊記號」，不用全體互等 | M8、M11：A100 上記號方式正確 |
| 收齊階段只用 1/8 執行緒 | 讓所有執行緒都參與，或改成主動推送 | M11 的拆解 |
| 搬資料只發揮 25–65% | 每次搬 16 byte（不要用 4 byte 原子加法）；例如 NCCL 在 A100 上已用的 LL128 寫法 | M11：4 byte 推送比 vLLM 慢；原子加法本身不是瓶頸 |

## 六、事實、推論、未知

**事實（重複量測）**
- 生成階段加總占每步 8–27%（M5）；最快的現成做法比可達水準慢 1.5–2.1 倍（M6）
- 連線使用率只有 10–31%（M11）
- vLLM 每次加總：等待占 kernel 內時間 34–42%（分兩次傳），另有 3.2–4.4 µs 空檔（M11）
- A100 上半精度原子加法：計數器到齊時資料一定加完（M8、M11，觀察非保證）；誤差 1.5e-3；每次結果會有些微不同（約 60% 的數值和上一次不完全一樣）
- 「各寫各的格子、負責人自己加」：正確、每次結果完全相同
- 4 byte 原子推送與 4 byte 格子寫入都比 vLLM 的對應步驟慢（M11）
- TensorRT-LLM、LMDeploy 的合併在 A100 上不比 vLLM 快（M9）

**推論（有數據支持，沒直接驗證）**
- M11 試作版慢，是因為一次只送 4 byte，而不是原子加法本身
- 空檔在新一代 GPU 上可以被 PDL 藏掉一部分
- 把空檔、等待、收齊階段都處理掉，320 KB 可以從 21 µs 降到 10 µs 左右

**未知**
- 用 16 byte 寫入加到齊記號（LL128 式）在 8 對 8、小資料時有多快
- 把加總和正規化放進同一步驟後，「整列到齊才能正規化」會不會變成新的等待
- 在 vLLM 裡端到端能快多少（目前只有估計 6–14%）
- 結論能不能推到其他沒有交換器內加總的 GPU（例如 L40S、PCIe 機器）

## 七、擱置的支線

- **F1：NCCL 一對一傳輸的通道分配**（M0、M4、M2）。機制完全清楚，改設定只能部分修好；AMD 的 RCCL 已經有修正（`lit/notes/nccl_p2p_channels.md`）。可以當另一篇的題目，目前不追
- **FLUX 式：把加總藏進前一步的矩陣計算**。生成階段的矩陣計算很短，能藏的有限；建議等加總本身做好再考慮
- **運算單元使用率**：通訊和計算同時跑時，計算會慢約兩成（M5）

## 八、規劃下一步時要決定的事

1. **論文主軸**（G2）：
   - 甲：系統論文。針對「沒有交換器內加總的 GPU」，做出一個生成階段專用的「加總＋正規化」，逐項消除第五節的時間預算，最後在 vLLM 端到端驗證
   - 乙：分析型論文。把「為什麼現有做法在 A100 上慢」寫清楚（第三、五節的拆解），附一個簡單的改進當示範
   - 丙：先做原型再決定
2. **新做法的資料傳遞方式**（M11 的判準要求先討論）：
   - 16 byte 寫入加到齊記號（LL128 式，不用原子加法，結果每次相同）
   - 讀取式（像 vLLM）但拿掉等待
   - 混合：小訊息一次全送，大訊息分兩次傳
3. **每一步怎麼驗證**：建議每加一個改進就量一次第五節的時間預算，這樣論文能說清楚每個改進各省了多少
