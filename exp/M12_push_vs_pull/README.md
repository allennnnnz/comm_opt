# M12_push_vs_pull

- **狀態**：完成（run `20261104_093500`）
- **核准**：2026-11-04（D025，使用者：「先做 a 看看，等等跟我講結果」——回應「先改良送資料的方式」）
- **類型**：結論性（3 次獨立執行、隨機順序）

## 白話結論

1. **「收齊結果」這一步，主動送和自己去拿一樣快，而且不用全體等待。** 在 80–640 KB，兩者差距在 17% 以內。和 vLLM「先全體等待、再去拿」相比，320 KB 以下快了 5.5–7.6 微秒（4.6–6.9 vs 12.2–12.4 微秒）。
2. **「分工加總」這一步，自己去拿明顯比較快**（主動送慢 1.6–2.6 倍）。所以分工加總維持 vLLM 的拿法。
3. **改成一次 16 byte 確實有效**：比上一次的 4 byte 版本快 1.8–2.0 倍（640 KB、1.25 MB）。
4. **大訊息（640 KB 以上）還沒解決**：這個測試程式在大訊息時，連「自己去拿」都比 vLLM 慢一倍，代表測試程式本身在大訊息有問題，還不能下結論。
5. **依事先定的標準：主動送夠快。** 新做法的第 ③ 步（拿掉中間等待），收齊結果用「送過去＋到齊記號」。


## 問題

在 8×A100 上，「主動送過去＋每 128 byte 附到齊記號」（LL128 式，每個執行緒一次 16 byte，不用原子加法）搬資料，能不能和 vLLM 的「自己去拿」（每個執行緒一次讀 16 byte）一樣快？答案決定新做法的第 ③ 步（用到齊記號取代中間等待）要用「送」還是「拿」。

## 已確認的事實（量測前）

- M11：4 byte 原子推送與 4 byte 格子寫入都比 vLLM 慢（1.25M：23.2／27.8 µs vs vLLM 起點等待＋第一階段 8.9 µs）；原子加法本身比 4 byte 一般寫入快 20%，所以推測問題在「顆粒太小、一次只有一件事在進行」
- M11 vLLM 2-stage 關鍵路徑（µs，80K／160K／320K／640K／1.25M）：第一階段 2.13／2.37／2.79／3.75／6.63；中間等待 4.90／4.75／4.80／5.58／5.78；第二階段（收齊）7.41／7.43／7.59／7.73／8.64
- NCCL 在 A100＋NVLink 上使用 LL128 協定（M0 的 tuner 在 2–8 MiB 選了 LL128）：每 128 byte 一行，其中 8 byte 是旗標，一個 warp 的一次 16 byte 寫入涵蓋 4 行，依賴「同一指令寫的 128 byte 一起送達」

## 設計（`ll128_probe.cu`，單一程序、8 張 GPU、peer access，計時方式同 M11 的 `rs_probe`）

大小 S = 80K／160K／320K／640K／1.25M（fp16，即 hidden 5120 × token 8–128），每張 GPU 負責 S/8。四種做法：

| 代號 | 階段 | 做法 |
|---|---|---|
| `ag_pull` | 收齊（all-gather） | 資料事先放好；每個執行緒一次讀 16 byte，同時讀 7 張卡（vLLM 第二階段的寫法） |
| `ag_push` | 收齊 | 每張卡把自己那 1/8 以 LL128 格式（每行 120 byte 資料＋8 byte 回合記號）一次 16 byte 寫到其他 7 張卡；收的一方檢查記號、到齊就把資料搬到輸出 |
| `rs_pull` | 分工加總（reduce-scatter） | 每個執行緒一次讀 16 byte，同時讀 8 張卡的同一段，fp32 依 0..7 順序相加（vLLM 第一階段的寫法） |
| `rs_push` | 分工加總 | 每張卡把第 k 段以 LL128 格式寫進負責人 k 的「第 r 格」；負責人等 8 格記號都到、依 0..7 順序 fp32 相加 |

- 起跑同步（不計時）後，每個 block 用 `clock64` 計時到自己的工作全部完成；一次的時間 = 所有 block、所有 GPU 的最大值
- `*_pull` 的資料在 kernel 開始前就已就位，所以**時間不含任何等待**——是「搬資料本身」的時間；`*_push` 的時間包含等記號
- block 數：16、32、64、108；每個執行緒 512 個／block；每次 launch 暖機 5 次、計時 50 次，每次之間清除緩衝區
- 檢查：收齊的結果逐位元等於原始資料；分工加總逐位元等於 host 依同樣順序算的 fp32 和（兩種做法應完全相同）；不符的 8 byte 數記為「違反」
- 比較以每種做法的最佳 block 數為準；3 次 launch 中位數的中位數與 [最小, 最大]

## 預期（量測前寫，量測後不改）

- **P1（正確）**：`ag_push`、`rs_push` 違反數 = 0
- **P2（收齊，送 vs 拿）**：`ag_push` ≤ 1.2 × `ag_pull` 的大小 ≥ 3/5
- **P3（分工加總，送 vs 拿）**：`rs_push` ≤ 1.2 × `rs_pull` 的大小 ≥ 3/5
- **P4（送＋記號 vs vLLM 的等待＋拿）**：`ag_push` 比 M11 的 vLLM「中間等待＋第二階段」（12.3–14.4 µs）快的大小 ≥ 3/5（我預期 5/5）
- **P5（改良有效）**：`rs_push` 在 640K、1.25M 比 M11 的 4 byte `store_slot`（17.4、27.8 µs）快 ≥ 1.5 倍

## 判準（量測前寫，量測後不改）

| 結果 | 條件 | 代表 |
|---|---|---|
| **主動送夠快** | P1 成立，且 P2 成立（≥ 3/5），且 P4 成立（≥ 3/5） | 第 ③ 步用「送過去＋到齊記號」 |
| **主動送不夠快** | P2 ≤ 1/5 | 第 ③ 步保留「自己去拿」，只把集合改成檢查記號 |
| **中間** | 其他 | 停下來討論 |

- P3 只影響「分工加總要不要也改成送」，不影響上面的判定
- P4 是跨程式比較（vLLM 數字來自 M11 的 CUDA graph 連續執行，本實驗是單次執行），只當參考方向；判定以 P2（同一個程式內比較）為主

## 已知風險

- LL128「同一指令的 128 byte 一起送達」是 NCCL 依賴的行為，不是文件保證；以違反數檢查
- 單次執行（每次清除緩衝區）和實際連續執行的情境不同（同 M11）

## 結論

| 預期 | 結果 | 判定 |
|---|---|---|
| P1：push 違反數 = 0 | 0 | 符合 |
| P2：`ag_push` ≤ 1.2 × `ag_pull` 的大小 ≥ 3/5 | 4/5（1.25M 為 1.34） | 符合 |
| P3：`rs_push` ≤ 1.2 × `rs_pull` 的大小 ≥ 3/5 | 0/5（1.63–2.61） | **不符** |
| P4：`ag_push` 比 vLLM「中間等待＋第二階段」快的大小 ≥ 3/5（預期 5/5） | 3/5（80K–320K 快；640K、1.25M 慢） | 符合判準，但不如預期 |
| P5：`rs_push` 在 640K、1.25M 比 4 byte store_slot 快 ≥ 1.5 倍 | 1.81、1.98 | 符合 |

- **判準結果：主動送夠快**（P1、P2 4/5、P4 3/5）→ 第 ③ 步的收齊用「送過去＋到齊記號」
- **分工加總維持「自己去拿」**（P3 0/5）。`rs_push` 在 80K 就固定要 6.8 µs，推測是負責人在同一個 warp 內依序等 8 格（設計可改，未驗證）
- **大訊息的疑點**：本程式的 `ag_pull` 在 640K、1.25M 是 16.1、22.8 µs，比 M11 的 vLLM 第二階段（7.7、8.6 µs）慢一倍以上，而兩者讀的資料量相同。可能原因（未驗證）：本程式單次執行、每次前清除緩衝區（vLLM 讀的是對方剛在第一階段寫入、還在快取裡的資料）；8 張卡同時依相同順序讀同一張卡。所以 640K 以上的 P4「不快」不能直接歸因於主動送
- **對新做法的意義**：320 KB 以下，「送過去＋到齊記號」可以取代 vLLM 的「中間等待＋收齊」，每次省約 5.5–7.6 µs；640 KB 以上要在真實的連續執行情境（以 vLLM 為底的原型）裡重新確認

### 限制

- 單次執行、每次清除緩衝區；跨程式比較（vs M11 的 vLLM）只當參考
- LL128「同一指令的 128 byte 一起送達」是觀察（0 次違反），不是文件保證
