# M13_push_retest

- **狀態**：完成（run `20261104_095803`）
- **核准**：2026-11-04（D027，使用者：「為何分工加總主動送比較慢？大資料量（640 KB 以上）這次測不準，這部份你要再去測一次」）
- **類型**：結論性（3 次獨立執行、隨機順序）

## 白話結論

1. **分工加總主動送慢，原因只找到一部分。** 負責人「一張一張檢查 8 張桌子」確實拖慢了，改成同時檢查後快了 12–30%，但還是比「自己去拿」慢 1.3–1.8 倍。剩下的原因還不確定，推測是主動送多繞了一趟：先寫到負責人那裡，負責人再讀出來加。依標準，這個假說**不成立**；分工加總維持「自己去拿」。
2. **大資料量測不準的原因找到了：是「每次清空、單次執行」的測試方式，不是讀取順序。** 改成實際的連續執行後，「自己去拿」在大資料快了約 3 倍，和 vLLM 的數字一致。錯開讀取順序沒有幫助。
3. **連續執行下，「主動送」在中小資料量的優勢確認了**：80–320 KB 收齊只要 4.0–4.5 微秒，vLLM「等待＋收齊」要 12.2–12.4 微秒。
4. **大資料量的主動送比不需要等待的「自己去拿」慢 14–22%**（1.25 MB 剛好超過 20% 門檻）。依事先定的標準，結論是「依大小切換」。但「自己去拿」實際上前面一定要先全體等一次。把這段算進去，主動送在 640 KB、1.25 MB 仍比 vLLM 快 6.9、3.4 微秒。要不要全部大小都用主動送，需要你決定。


## 問題

1. M12 的分工加總，「主動送」為什麼比「自己去拿」慢 1.6–2.6 倍？
2. M12 在 640 KB 以上，連「自己去拿」都比 vLLM 慢一倍——是測試方式造成的嗎？在接近實際的情境下，「主動送」的收齊還夠快嗎？

## 已知（M12，量測前）

- `rs_push` 在 80K 就固定要 6.8 µs；負責人在同一個 warp 內**依序**等 8 格（等第 s 格到齊才去看第 s+1 格），而 `rs_pull` 一次發出 8 個讀取
- `ag_pull` 在 640K／1.25M 是 16.1／22.8 µs，M11 的 vLLM 第二階段（讀的資料量相同）只要 7.7／8.6 µs。兩者差在：(a) M12 每次執行前清除緩衝區、單次執行，vLLM 是 CUDA graph 連續執行、讀的是對方剛寫入的資料；(b) M12 的 8 張 GPU 都依 0..7 的相同順序讀，vLLM 每張 GPU 從 (rank+1) 開始輪流

## 假說

- **H1**：`rs_push` 慢是因為依序等 8 格。改成 8 格同時讀取、同時檢查記號（`rs_push_par`），就會接近 `rs_pull`
- **H2**：大資料量慢有兩個可能原因——讀取順序撞在同一張 GPU（H2a），以及單次執行加清除緩衝區（H2b）
- **H3**：在連續執行的情境下，`ag_push` 在 640K、1.25M 仍與 `ag_pull` 差不多快

## 設計（`m13_probe.cu`，由 M12 的 `ll128_probe.cu` 延伸）

做法（M12 的四種照舊，另加兩種）：

| 代號 | 說明 |
|---|---|
| `ag_pull`、`ag_push`、`rs_pull`、`rs_push` | 同 M12 |
| `ag_pull_rot`（新） | 同 `ag_pull`，但每張 GPU 從 (rank+1) 開始輪流讀（vLLM 的順序） |
| `rs_push_par`（新） | 同 `rs_push`，但負責人一次對 8 格發出讀取、同時檢查 8 個記號，有沒到的才重讀 |

兩種模式：

- **單次模式**（同 M12）：每次清除緩衝區、起跑同步、`clock64` 計 kernel 內時間
- **連續模式**（新）：每張 GPU 把 K=20 次執行錄成 CUDA graph，重播 20 次（同 M6／M11）；不清除緩衝區、沒有起跑同步。回合記號由每個 block 自己的計數器遞增（同 vLLM 的作法），主動送的接收區依回合單雙數輪流用兩份（每次每張 GPU 都會收到所有人的資料，所以回合 e+2 寫入時，接收者一定已讀完回合 e）。報兩種時間：kernel 內時間（每次執行最慢 block 的 `clock64`，取中位數）與事件量到的每次時間
- 「拿」的資料在兩種模式都事先放好且不變（只量搬資料）；正確性：連續模式每個設定最後一次的輸出逐位元比對

其他：大小 80K–1.25M（5 種）、block 數 16／32／64／108、每個執行 3 次獨立 launch、隨機順序；比較取每種做法的最佳 block 數，3 次中位數的中位數與 [最小, 最大]。

## 預期（量測前寫，量測後不改）

- **P1（H1）**：單次模式下，`rs_push_par` ≤ 1.2 × `rs_pull` 的大小 ≥ 3/5
- **P2（H2a）**：單次模式下，`ag_pull_rot` 在 640K、1.25M 比 `ag_pull` 快 ≥ 1.3 倍
- **P3（H2b）**：連續模式下，`ag_pull_rot` 在 640K、1.25M 的 kernel 內時間 ≤ 1.3 × M11 的 vLLM 第二階段（7.73、8.64 µs）
- **P4（H3）**：連續模式下，`ag_push` 在 640K、1.25M 的 kernel 內時間 ≤ 1.2 × `ag_pull_rot`
- **P5**：連續模式下，`ag_push` 在 80K–320K 的 kernel 內時間仍比 M11 的 vLLM「中間等待＋第二階段」（12.2–12.4 µs）快

## 判準（量測前寫，量測後不改）

| 結果 | 條件 | 代表 |
|---|---|---|
| **收齊全部大小都用主動送** | P4 成立（640K、1.25M 都 ≤ 1.2 倍）且 P5 成立 | 新做法收齊一律「送過去＋到齊記號」 |
| **依大小切換** | P5 成立但 P4 不成立 | 小訊息用主動送；大訊息保留「等待＋拿」 |
| **停下來討論** | P5 不成立 | 連小訊息的優勢在連續情境下都不存在 |
| H1 成立 | P1 成立 | 分工加總慢的原因確認；是否改用 `rs_push_par` 另外討論（M12 已決定分工加總用拿法） |

- P2、P3 用來說明 M12 大資料量「測不準」的原因，不影響上面的設計判定

## 結論

| 預期 | 結果 | 判定 |
|---|---|---|
| P1：單次模式 `rs_push_par` ≤ 1.2 × `rs_pull` 的大小 ≥ 3/5 | 0/5（1.26–1.77 倍）；比 `rs_push` 快 12–30% | **不符** |
| P2：單次模式 `ag_pull_rot` 在 640K、1.25M 比 `ag_pull` 快 ≥ 1.3 倍 | 1.00、1.08 倍 | **不符** |
| P3：連續模式 `ag_pull_rot` 在 640K、1.25M ≤ 1.3 × vLLM 第二階段 | 5.67 ≤ 10.05、9.05 ≤ 11.23 | 符合 |
| P4：連續模式 `ag_push` 在 640K、1.25M ≤ 1.2 × `ag_pull_rot` | 1.14（符合）、1.22（不符） | **不符**（1/2） |
| P5：連續模式 `ag_push` 在 80K–320K 比 vLLM「中間等待＋第二階段」快 | 4.04／4.09／4.52 vs 12.31／12.17／12.39 | 符合 |

- **判準結果：依大小切換**（P5 成立、P4 不成立）——小訊息收齊用主動送；大訊息依判準保留「等待＋拿」
- **H1 只部分成立**：依序等 8 格解釋了一部分（快 12–30%），剩下 1.3–1.8 倍的差距原因未知。推測（未驗證）：主動送的分工加總多一趟本地讀寫（先寫進負責人的格子，再讀出來加），而且用的是系統範圍的強一致寫入
- **M12 大資料量「測不準」的原因是 H2b（單次執行＋清除緩衝區），不是 H2a（讀取順序）**：同一個 `ag_pull` 從單次 16.85／24.79 µs 降到連續 5.32／8.68 µs
- **判準沒涵蓋、但和設計直接相關的一點**：P4 比的是「不用等待的拿」，但實際的「拿」前面一定要有一次全體等待（vLLM 約 5.6–5.8 µs）。連續模式 `ag_push` 在 640K、1.25M（6.44、11.03 µs）仍比 vLLM「中間等待＋第二階段」（13.31、14.42 µs）快。是否把主動送用在所有大小，`[需裁決]`

### 限制

- 跨程式比較：vLLM 的數字來自 M11（同樣是 CUDA graph 連續執行，但程式不同）
- 連續模式的 kernel 內時間包含等待其他 GPU（取代 barrier 的部分），這正是要比較的
