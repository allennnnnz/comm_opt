# M17_epoch_ab

- **狀態**：完成（run `20261104_105218`）
- **核准**：2026-11-04（D036，使用者：「查清楚漏洞是什麼、為何修好後影響效能了、修之前量的數據是怎樣」）
- **類型**：結論性（同一次 run 內交錯比較，3 次獨立 launch）＋正確性測試

## 白話結論

1. **M16 量到的大幅變慢，主要是那次量測時機器比較慢，不是修法造成的。** 這次把新舊版放在同一次量測裡交替跑，修正版只比舊版慢 2–7%（M16 跨兩次量測比是 9–25%）。
2. **修法真正的代價很小，而且去掉多餘的等待步驟後幾乎消失**：去掉等待步驟的修正版和舊版差 0.3–3.5%，交錯測試 120/120 正確。依標準：**採用這個版本當正式修正版**。
3. **修正版對 vLLM 的倍數**：16／32／64 人時為 1.28／1.55／1.32 倍。16 人那一格從舊版的 1.33 掉到 1.28，**略低於原本 1.3 的成功門檻**；32、64 人仍明顯超過。
4. **M14、M15 的結論大致成立，但 16 人那一格要改成「約 1.3 倍」，不能說穩定超過 1.3。**


## 問題

M16 的修正版量到比 M15 慢 9–25%，但同一次 run 的 vLLM（沒改過）也慢 3–13%。到底是修法本身的代價、還是兩次量測時機器狀態不同？如果是修法的代價，是哪一部分造成的、能不能去掉？

## 三個版本的差別（量測前，讀程式）

| 版本 | epoch 怎麼來 | kernel 結尾多做的事 |
|---|---|---|
| `m15`（舊版，有漏洞） | 每個 block 讀自己的計數器 `ctr[blockIdx]` | thread 0 寫回 `ctr[blockIdx]` |
| `m16`（M16 修正版） | 所有 block 讀同一個全域 `ctr[0]` | thread 0：`__threadfence()` → `atomicAdd(done)` → 最後一個 block 歸零 done、寫 `ctr[0]`、再 `__threadfence()` |
| `m16nf`（新：去掉 fence） | 同 `m16` | 同 `m16`，但不做兩次 `__threadfence()` |

- 為什麼 fence 可能不必要：每個 block 的 epoch 在 kernel 一開始就讀出，而且立刻用在 start barrier（寫進 peer 的 flag、拿來比較），所以讀取一定在這個 block 做 `atomicAdd(done)` 之前完成；最後一個 block 要等所有 block 都做完 `atomicAdd` 才會寫新的 epoch，所以不會有人讀到新值。下一次 kernel 依 stream 順序在這次結束後才開始，自然看得到新的 epoch
- 為什麼 fence 可能很貴：`__threadfence()` 要等這個 thread 之前送出的寫入對整個 GPU 可見；thread 0 在 all-gather 階段送出過跨卡 LL128 寫入，可能要等 NVLink 確認（推測）

## 設計

- **正確性**：`m16nf` 跑 M16 的交錯測試（eager 與 CUDA graph 各 60 次，token 1／3／8／13／40／64／128 × block 16／32／64／108）
- **速度**：一個測試程式同時載入三個版本（各自編譯），和 `U_vllm` 一起在**同一次 launch 內依隨機順序交錯**量測（計時方式同 M14–M16：CUDA graph K=20 × R=20，8 個 rank 取最大）。fp16、hidden 5120、token 8–128；每個版本 block 數 16／32／64／108，取最佳。3 次獨立 launch
- 每個設定之間重設接收區、flag、計數器（三個版本共用同一組 symmetric buffer）

## 預期（量測前寫，量測後不改）

- **P1**：`m16nf` 交錯測試 120/120 正確
- **P2**：同一次 run 內，`m16` 比 `m15` 慢 > 5% 的大小 ≥ 3/5（修法確實有代價）
- **P3**：`m16nf` 與 `m15` 相差 ≤ 5% 的大小 = 5/5（代價來自 fence）

## 判準

| 結果 | 條件 | 代表 |
|---|---|---|
| **採用 `m16nf`** | P1 且 P3 成立 | 以 `m16nf` 為正式修正版；M14／M15 的速度結論不變 |
| **代價在全域 epoch 本身** | P1 成立、P3 不成立 | 停下來討論（例如改成不需要計數的 epoch 設計） |
| **去掉 fence 不安全** | P1 不成立 | 保留 `m16`，查原因 |

- P2 只用來確認 M16 的變慢有多少是修法本身造成；若 P2 不成立，代表 M16 的變慢主要來自機器狀態

## 結論

| 預期 | 結果 | 判定 |
|---|---|---|
| P1：`m16nf` 交錯測試 120/120 正確 | 120/120 | 符合 |
| P2：同一次 run 內 `m16` 比 `m15` 慢 > 5% 的大小 ≥ 3/5 | 1/5（只有 80K 7.2%；其他 1.8–4.2%） | **不符**——M16 的大幅變慢主要來自機器狀態 |
| P3：`m16nf` 與 `m15` 相差 ≤ 5% 的大小 = 5/5 | 5/5（0.3–3.5%） | 符合 |

- **判準結果：採用 `m16nf`**（`exp/M17_epoch_ab/fused_ar_norm_nf.cu` 為正式修正版）
- **回答使用者的三個問題**：
  - 漏洞：每個 block 各自計 epoch，交錯使用不同 block 數時，送與收的 epoch 對不上 → 卡住（M16 實測重現）
  - 修好後為什麼變慢：M16 的 9–25% 是跨 run 比較，同一次 run 內修法的代價只有 2–7%（`m16`），去掉 fence 後 0.3–3.5%（`m16nf`）。M16 那次 run 的機器狀態原因未查（vLLM 也慢 3–13%）
  - 修之前的數據：M14／M15 量測時每個設定用固定 block 數且重設計數器，漏洞沒有觸發、結果都正確，數字是舊版的真實速度；但正式結論應改用 `m16nf`。對 vLLM 的倍數：160K 由 1.30–1.35（舊版，三次 run）變成 1.28，320K、640K 仍 1.55、1.32
- **跨 run 變異是新的風險**：同一份程式在不同 run 之間可以差 10% 以上（M15 vs M16），所以之後的比較一律放在同一次 run 內交錯量測
