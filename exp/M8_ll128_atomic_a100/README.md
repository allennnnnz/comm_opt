# M8_ll128_atomic_a100

- **狀態**：完成（run `20261103_095424`；`20261103_094100` 為修正前卡住而中止的紀錄）
- **核准**：2026-11-03（D016，使用者：「好 先做第一步」——確認《Every µs Matters》的 two-shot LL128 atomic 在 A100 上是否可行）
- **類型**：可行性測試（3 次獨立執行）

## 白話結論

1. **這個做法很可能可以搬到 A100 上，和我的預期相反。** 7 張 GPU 同時對 100 萬個 128 byte 的區塊做原子加法，重複 3 次，從來沒有出現「旗標已滿、資料卻還沒加完」的情況；觀察者有大約四分之一的區塊是在寫入途中看到的，所以測試確實有能力抓到問題。
2. **但不能照論文原樣搬。** 論文用的是「一次加 16 bytes」的向量原子加法，A100 沒有這個指令（只有新一代 GPU 有）。改成 32 個執行緒各加 4 bytes，A100 在這次測試中仍表現得像「整個區塊一起生效」。
3. **跨 GPU 原子加法夠快。** 7 張 GPU 一起加進 1 張 GPU，總共 235–241 GB/s，接近這台機器實測的最高頻寬。
4. **對研究的影響：新穎性風險升高。** 論文提出的免 barrier 分兩次傳，在 A100 上看起來是做得到的；如果我們只是把它搬過來，貢獻會偏弱。需要重新想我們能多做什麼。
5. **注意**：「沒看到違反」不等於「硬體保證」，這是觀察結果，不是 NVIDIA 文件寫明的性質。

## 問題

《Every µs Matters》（Shen et al., arXiv 2607.16100）的 two-shot LL128 atomic all-reduce 能不能在 A100 上正確運作？它的前提是（論文 §IV-4）：「NVLink 會在 cache line（128 bytes）層級原子地套用這些原子加法」與「NVLink 原子地執行 128 byte 的寫入」——所以接收端看到該行的旗標（第一個元素）等於 rank 數 N 時，該行其他元素一定也已加總完成。論文只在 GB200 上評估，沒有提到 A100。

## 已確認的事實（量測前，讀論文與原始碼）

- 論文 Table I：two-shot LL128 atomic 的同步次數是 **2**（不是 1），資料量約 2(N−1)M/N；它去掉的是全域 memory barrier，改用嵌在資料裡的旗標
- 公開的 low-latency-nccl 分支（commit 5357eff）**沒有** LL128 atomic 的實作（搜尋 `LL128_Atomic` 0 筆）；有 LL 與 sentinel（Poison）兩種同步模式的 one-shot／two-shot
- 該分支把所有新增做法（包含不需要 multicast 的 LL／sentinel 版本）列在 `nvls_algos_by_coll`，因此只在 `__CUDA_ARCH__ >= 900` 時編譯 kernel 內容；A100（sm80）上 kernel 是空殼——這解釋了 M7 試跑「1.5 µs、結果全錯」
- NCCL 本身在 A100 + NVLink 上會選用 LL128 協定（M0 tuner 在 2–8 MiB 選了 LL128），代表一般的 128 byte **寫入**在 A100 NVLink 上被 NCCL 視為原子；**原子加法**是否有同樣性質未知

## 測試設計

單一程序、8 張 GPU、開啟 peer access（`test_ll128_atomic.cu`，nvcc `-arch=sm_80`）：

1. **向量原子加法是否存在**：嘗試為 sm_80 編譯 `red.global.add.v4.f32`（16 bytes 一次）——預期 ptxas 拒絕（需要 sm_90）
2. **cache line 層級原子性**：GPU0 上配置 T = 2^20 個 128 byte 的行（每行 32 個 uint32）。8 張 GPU 同時對每一行做 warp 寬度的原子加法：lane 0 對第 0 個元素（旗標）加 1，lane 1–31 對自己的元素加 (rank+1)。GPU0 同時跑觀察者：每個 warp 以一次 warp 寬度的讀取讀整行，旗標 = 8 時檢查其餘 31 個元素是否都 = 36（1+…+8）。違反 = 「旗標已到 8，但資料還沒加完」
   - **測試程式的修正（量到核心數據之前）**：第一次執行時 GPU0 也寫入，但 GPU0 上的寫入 kernel 沒有和忙等的觀察者同時執行，旗標停在 7，觀察者卡住（`results/M8_ll128_atomic_a100/20261103_094100/` 為這次中止的紀錄，`run.log` 空白）。改成只有 GPU1–7 寫入（全部經過 NVLink），旗標目標 7、資料目標 35（2+…+8）；這正是 LL128 atomic 前提所描述的情況（遠端原子加法）
3. **跨 GPU 原子加法的速度**：計時 8 張 GPU 的寫入 kernel，換算每張 GPU 的原子加法頻寬

## 預期（量測前寫，量測後不改）

- 1：sm_80 不支援 `red.global.add.v4.f32`（16 byte 向量原子加法是 sm_90 起才有）
- 2：會出現違反（> 0）。A100 上每個 32-bit 原子加法是獨立的 NVLink 交易，沒有理由在 cache line 層級一起生效
- 3：跨 GPU 原子加法頻寬遠低於一般寫入（低於 50 GB/s／GPU）

## 判準（量測前寫，量測後不改）

| 結果 | 條件 | 代表 |
|---|---|---|
| LL128 atomic 前提在 A100 上不成立 | 3 次執行中任一次違反數 > 0（旗標 = 7 但資料 ≠ 35） | 這個做法不能直接搬到 A100；A100 需要其他方式做到免 barrier 的 two-shot |
| 前提在 A100 上可能成立 | 3 次執行、每次 2^20 行，違反數都 = 0 | 新穎性風險高；要再確認效能 |

- 違反數 = 0 不能證明「保證成立」（只是沒觀察到）；違反數 > 0 則足以否定
- **檢定力**（量到核心數據之前補）：另記錄 `raced_lines` = 觀察者在旗標未滿時就看到、之後才看到它滿的行數。若 raced_lines 太少（< 1% 的行），違反數 = 0 沒有意義，判為「無法判定」

## 結論

| 預期 | 結果 | 判定 |
|---|---|---|
| sm_80 不支援 16 byte 向量原子加法 | 不支援 | 符合 |
| 會出現違反（> 0） | 3 × 2^20 行，0 次違反；約 25% 的行在寫入途中被觀察到 | **不符** |
| 跨 GPU 原子加法頻寬 < 50 GB/s／GPU | 每張寫入 GPU 34 GB/s，但這是 7 對 1 的情況，受 GPU0 的接收端限制；匯入總頻寬 235–241 GB/s | 數字符合，但解讀需修正：瓶頸在接收端，總量接近連線上限 |

- **判準結果**：「前提在 A100 上可能成立」（3 次、每次 2^20 行，違反數都 = 0；raced 比例 25% > 1%）
- **解讀**：A100 的 NVLink 在這個測試中，對一個 warp 打到同一個 128 byte 行的 32 個 4-byte 原子加法，表現得像整行一起套用。這與論文對新一代 GPU 的描述一致，但論文沒有測 A100，NVIDIA 文件也沒有寫明
- **對新穎性的影響**：two-shot LL128 atomic 的核心機制在 A100 上很可能可行（需改用 32-bit 原子加法）。「把它搬到 A100」本身的論文貢獻偏弱

### 限制

- 違反數 = 0 是觀察，不是保證；只測了 uint32 加法，沒測 fp16／bf16 的原子加法（`f16x2`、`bf16x2`）
- 觀察者在 GPU0 本地讀取；真實演算法的讀取方式（向量讀取、旗標位置）可能不同
- 只測了 7 對 1；all-reduce 的 reduce-scatter 是 8 對 8 同時進行
