## 問題

單節點內五個候選題目，各自的關鍵數字是多少？用同一台 8× H100、同一張 2 小時的工作量完：

| 題目 | 關鍵數字（本卡要量） | 區塊 |
|---|---|---|
| T1 通訊與計算同時跑時的做法選擇 | 同時跑矩陣乘法時，「單獨跑最快的通訊設定」和「整體最快的設定」是否不同、差多少；矩陣乘法被拖慢多少 | B1 |
| T2 生成時的小訊息加總 | vLLM 張量平行生成時，加總佔每個字 GPU 時間的比例（批次 1–128） | B2 |
| T3 機器內交換晶片加總（NVLS）何時該用 | NVLS 開／關、各演算法的速度曲線；NCCL 預設是否選錯；512 MB 當機能否重現 | B3、B4 |
| T4 混合專家模型的機內通訊 | 專家平行（EP）與張量平行（TP）生成時的通訊比例；全員互傳曲線 | B2、B3 |
| T5 機內預填／生成分離的快取搬運 | 一個長請求的快取搬運時間 ÷ 它的預填時間 | B2、B3 |

### 判讀規則（決定題目時用；寫於量測前）

- T1 成立：O4 成立的格數 ≥3，且至少一格矩陣乘法變慢 ≥10%
- T2 成立：I2 或 I3 顯示某個批次的通訊比例 ≥20%（優化上限才夠大）
- T3 成立：C3 成立，或 NVLS 有可重現的失敗／反常
- T4 成立：EP 的通訊比例 ≥30%
- T5 成立：I5 被推翻（搬運 ≥ 預填 10%）
- 多個成立時，Opus 列出並排比較，由使用者選

## 設定

- **GPU**：單台 H100 整台，`dev`（上限 2 小時；2026-11-17 試算 `dev` 約當天下午可開始，`normal` 要到 11-18 20:05）。`--exclusive` 會被叢集拿掉，以 `cotenants.sh` 記錄（D054）。開始前檢查 8 張卡上沒有其他 GPU 行程（R13）
- **固定條件**：NCCL 2.29.7（venv）；nccl-tests v2.21.1，用 `mpirun` 啟動（M20：只有它能用）；PyTorch 2.13.0+cu129、vLLM 0.32.0+cu129（venv 的 Python 修好後）；驅動 550.127.08
- **時間預算與順序**（全工作一個截止時間；每個區塊開始前檢查剩餘時間，超時就跳到下一塊；單次啟動失敗只記錄、不中止）：
  1. B0 環境紀錄、GPU 行程檢查、60 秒暖機；全程背景記錄時脈／功率／溫度（每 0.5 秒）— 約 4 分
  2. B4 NVLS 當機（N1、N2）— 上限 8 分
  3. B1 通訊與矩陣乘法同時執行（O1–O4）— 上限 30 分
  4. B2 vLLM 推論（I1–I5）— 上限 40 分
  5. B3 集體通訊曲線（C1–C5）— 上限 25 分
- **B1 細節**：
  - 集體通訊：all_reduce、reduce_scatter、all_gather；大小 4、32、256 MB
  - 矩陣乘法：8192×8192×8192 與 4096×4096×4096（bf16）
  - NCCL 設定（每個設定一次獨立啟動，2 次，順序打亂）：預設；Ring；Ring＋CTA 4／8／16／32（`NCCL_MIN_CTAS`=`NCCL_MAX_CTAS`）；NVLS；NVLS＋`NCCL_NVLS_NCHANNELS` 4／8；`NCCL_CTA_POLICY=EFFICIENCY`
  - 每格量三種情況：矩陣乘法單獨、通訊單獨、兩者同時（各在一條 stream 上，同時開始）；工作量固定（通訊次數在每格開始時用預設設定校準為「單獨時間約為矩陣乘法的一半」，之後所有設定沿用同一個次數）
  - 指標：矩陣乘法變慢 %、通訊變慢 %、同時執行的總時間；實際 CTA／channel 數從 NCCL 初始化日誌取得
- **B2 細節**（每個引擎一次啟動，引擎內重複多次）：
  - Qwen2.5-72B-Instruct（dense，80 層，hidden 8192）：TP=8 解碼批次 1／8／32／128（輸入 1024、輸出 128）；TP=8 預填 1k／4k／16k（批次 1）；TP=4 預填 1k／4k／16k 與解碼批次 1／32
  - Qwen3-30B-A3B（MoE）：TP=8 與 TP=8＋專家平行，解碼批次 1／32／128
  - 通訊比例：用 PyTorch profiler（vLLM 內建的 profiler 介面）抓 rank 0 的 kernel 時間，依 kernel 名稱分類（加總、其他集體通訊、矩陣乘法、注意力、其他）。CUDA graph 下若抓不到個別 kernel，改用 eager 模式抓比例、另報 CUDA graph 下的每字時間
  - 記錄 vLLM 實際選的加總實作（自製 all-reduce／NCCL／其他）
- **B3 細節**（2 次獨立啟動，順序打亂；8 B–1 GB，每次 ×2；`-a 3` 跨 rank 取最大值）：
  - 8 卡 all_reduce：預設、Ring／LL、Ring／LL128、Ring／Simple、Tree、NVLS、NVLS 關
  - 8 卡 reduce_scatter、all_gather：預設、NVLS 關；8 卡 alltoall：預設
  - 2 卡 sendrecv（GPU 0↔1）：預設、`NCCL_P2P_USE_CUDA_MEMCPY=1`
  - 4 卡、2 卡 all_reduce：預設
  - 每個設定另跑一次 `-n 1` 的選擇日誌（`NCCL_DEBUG_SUBSYS=TUNING`），以實際使用的演算法為準
- **統計方式**：每個設定報中位數與全距（2 次啟動或引擎內重複）；探索性，不做信賴區間結論
- **理論上限**（R8）：每張 H100 NVLink 單向約 450 GB/s（18 條 × 25 GB/s，M20 待核實）；HBM 3.35 TB/s
