# M18_incremental

- **狀態**：進行中（步驟 a 完成，下一步 b）
- **核准**：2026-11-04（D038，使用者：「這些先做。我要你每個都一點點加入，確定逐漸優化都確實有效才往下加下一個，找出這幾個優化項目中最好的組合」）
- **類型**：逐步加入、每步同一次 run 內 A/B（5 次獨立 launch）＋正確性測試

## 白話結論

**步驟 a（查清偶爾變慢）完成：原因找到，新的量測方式採用。**

1. **偶爾變慢是 GPU 時脈造成的。** 沒有暖機時，GPU 量測時多半跑在 1155–1260 MHz，而且排在前面量的設定比較慢；先讓所有 GPU 忙 2 秒再量，時脈穩定在最高的 1410 MHz，每次量測之間的差距從最多 21% 降到 5% 以內。
2. **另外發現：每次量測的第一個設定一定特別慢**（不管有沒有暖機），之後要先丟掉一個暖身用的設定再開始記錄。
3. **時脈變高後，原型對 vLLM 的倍數改變了**（同一次量測、固定 64 組）：16／32／64／128 人為 1.22／1.71／1.41／1.38 倍；**1–4 人時原型反而比 vLLM 慢**（0.85–0.97 倍），這正是步驟 c（小資料改用一次全送）要解決的。
4. 之前 M14–M17 的數字都是在較低時脈下量的；同一次量測內的比較仍然成立，但絕對數字和這次之後的不能直接比。


## 問題

把五項改善（依大小選 block 數、小訊息用 one-shot、拿掉 start barrier、大訊息換做法、查清偶爾變慢）一項一項加到原型上，每一項都確認「正確」且「確實變快」才保留，最後得到最好的組合。

- **v0** = M17 採用的 `m16nf`（`exp/M17_epoch_ab/fused_ar_norm_nf.cu`），**固定 64 個 block**（M17 中最常是最佳的數字）。之前報告的「最佳 block 數」是事後從 4 種裡挑最好的，等於偷看答案；從這裡開始，block 數的選擇必須事先決定，或由另一次 run 校準出來

## 共同規則（每一步都適用，量測前寫）

- **正確性**：新版本先過 M16 的交錯測試（`exp/M16_epoch_fix/test_interleave.py`；eager 與 CUDA graph 各 60 次，token 1／3／8／13／40／64／128 × 不同 block 數）。任何一次錯誤 → 這一步不採用，停下來查
- **速度**：同一次 run 內交錯量測「上一步的最佳版本」、「這一步的新版本」、vLLM（`U_vllm`），fp16、hidden 5120，token 1／2／4／8／16／32／64／128（10K–1.25M），CUDA graph K=20 × R=20、8 個 rank 取最大；**5 次獨立 launch**，每次的中位數再取中位數，區間 = 5 次的 [最小, 最大]
- **「有效」**：在某個大小，新版本中位數快 ≥ 3%，且區間不重疊
- **「變差」**：在某個大小，新版本中位數慢 ≥ 3%，且區間不重疊
- **保留規則**：在這一步的目標大小中至少一個「有效」→ 保留；若有其他大小「變差」→ 只在「有效或沒差」的大小使用新做法（依大小切換），這樣組合不會在任何大小比上一步差
- **校準與驗證分開**：凡是要從多個選項中挑最好的（block 數、切換門檻），先用一次「校準 run」挑，再用另一次「驗證 run」量效果，避免挑選偏差
- 預期與實際矛盾時，依上面的規則決定保留或捨棄並照實記錄；正確性失敗或出現無法解釋的現象才停下來問使用者（使用者 2026-11-04 要求逐步自動推進，見 D038）

## 步驟、預期與做法

### 步驟 a：查清偶爾變慢（改善 5，量測方法）

- **觀察（量測前）**：M14、M15 的 hidden 5120 第 1 次 launch、hidden 8192 第 1、2 次 launch，原型都慢 2–5 µs；這些 launch 裡原型 64 blocks 都排在最前面幾個被量。GPU 閒置時 SM 時脈 210 MHz，工作中 1155 MHz；目前每個設定的暖機只有 5 次呼叫＋3 次 graph 重播（幾毫秒）
- **假說**：排在前面的設定量到時，GPU 還沒升到工作時脈
- **做法**：測試程式記錄每個設定量測前的 SM 時脈（NVML）；加入「開始前 2 秒全卡忙碌暖機」＋「每個設定 50 次 graph 重播暖機」。舊方式（不暖機）與新方式各跑 5 次 launch，v0 與 vLLM
- **預期**：舊方式下，慢的設定對應較低的時脈；新方式下，v0 在 16K–640K 的 launch 間最大／最小比 ≤ 1.05，舊方式至少有一個大小 > 1.05
- **保留規則**：預期成立 → 之後所有步驟用新方式量測

- **中止的第一次執行**（`results/M18_incremental/a_20261104_152116/`，保留不刪）：只完成 `old_s1`；`new_s1` 在暖機階段卡住 10 分鐘後被 NCCL watchdog 中止（rc=1），之後整個 run 隨上一個工作階段結束而中斷。原因是測試程式的錯誤：暖機迴圈每張 GPU 各自看時間決定何時停，跑的輪數不同，而每一輪都有一次全體 all-reduce → 多跑一輪的 GPU 永遠等不到其他人。修正：每輪結束時全體以 all-reduce（取最小值）決定是否繼續。修正後小試跑（不採用）正常，但看到兩個現象待正式數據確認：暖機後 SM 時脈讀到 1410 MHz（不是之前以為的固定 1155）；暖機後第一個量的設定（vLLM、8 tokens）異常慢（417 µs）。`figures/M18_incremental/a_20261104_152116/` 是使用者稽核時對這次不完整資料跑的分析，僅供參考

### 步驟 b：依大小選 block 數（改善 1）

- **做法**：block 數掃 16／24／32／48／64／80／96／108。校準 run 挑出每個大小最快的 → 寫成表；驗證 run 比較 v0（固定 64）與 v0＋表
- **預期**：至少 2 個大小「有效」；160K 對 vLLM ≥ 1.3 倍

### 步驟 c：小訊息用 one-shot（改善 2）

- **做法**：新增 one-shot 路徑：每張 GPU 用 LL128 把自己整份輸入推給其他 7 張（不需要 start barrier），每張 GPU 自己把 8 份相加、加 residual、做 RMSNorm（每張都算全部的列，residual 保持完整）。校準 run 找出 one-shot 比 two-shot 快的 token 數範圍 → 切換門檻；驗證 run 比較
- **預期**：token ≤ 4 時 one-shot 快 ≥ 10%；切換點在 8 到 16 之間

### 步驟 d：縮短或拿掉 start barrier（改善 3）

- **做法**：兩個候選——(i) 分段 barrier：先送出「我準備好了」的訊號，趁等待時先讀本地的 residual／gamma，真的要讀別人的資料前才等；(ii) reduce-scatter 改用 push（M13 的 `rs_push_par`），完全不需要 start barrier。兩者都量，保留較好的
- **預期**：(i) 在中間大小省 0.3–1 µs（3–8%）；(ii) 不比 (i) 好（M13：push reduce-scatter 慢 1.3–1.8 倍）

### 步驟 e：大訊息換做法（改善 4）

- **做法**：目前每一列只由一個 block 做 reduce-scatter＋norm，token 128 時每張 GPU 只有 16 列 → 只有 16 個 block 在做第一階段。改成每列拆給 2 或 4 個 block，平方和用 block 間的原子加法合併。量 token 64／128／256
- **預期**：token ≥ 64 時「有效」（快 ≥ 5%）

### 最後：最佳組合確認

- 保留的改善全部合在一起，與 vLLM、TRT-LLM 合併在同一次 run 比較：fp16／bf16、hidden 5120／8192、token 1–256，5 次 launch
