## 問題

在真實的推論與訓練中，GPU 之間的通訊占了端到端時間的多少？其中多少被計算「藏住」、多少真的拖慢了整體？通訊實際用的資料大小，落在 M0 量到的頻寬曲線的哪一段？

## 量法（依文獻）

- **時間分解**（Mirzaei & Mitra 2610.05305 把延遲拆成計算、通訊、空檔；Chopper 2512.08242 從單一 kernel 到整個 iteration 對齊 GPU timeline）：用 PyTorch profiler 取得每張卡的 GPU kernel timeline，把每個步驟的牆鐘時間切成四塊，加起來 = 100%：
  - **只有計算**：有計算 kernel、沒有通訊 kernel
  - **只有通訊（沒藏住）**：有通訊 kernel、沒有計算 kernel → 這就是「通訊占端到端的時間」
  - **重疊**：兩者同時在跑
  - **空檔**：GPU 都沒事（CPU 準備、kernel 發射的間隙）
- **通訊 kernel 的認定**：名稱含 `nccl`（NCCL）或 vLLM 自己的 all-reduce kernel（`cross_device_reduce` 等）；實際用到的 kernel 名稱清單記在結果裡，分類規則寫在分析腳本
- **隱性代價**（Lee et al. 2507.03114：重疊時計算平均變慢 18.9%）：同一個計算 kernel（同名、同 grid）在「有通訊同時跑」和「沒有」時的執行時間中位數比較
- **訊息大小**：從 profiler 的 collective 資訊（元素數、型別、群組大小）取得；對照 M0 的頻寬曲線，算「如果跑到 nccl-tests 的峰值，能省多少」
- **GPU 時脈**（Chopper 發現時脈波動是效率差距的最大來源）：量測期間每 100 ms 記錄每張卡的 SM clock 與溫度

## 工作負載

| 情境 | 框架 | 模型 | 平行方式 | 變因 |
|---|---|---|---|---|
| 推論 | vLLM 0.33.0（預設設定，含 CUDA graph 與 vLLM 自己的 all-reduce） | 中型：Qwen2.5-32B-Instruct；小型：TinyLlama-1.1B | 模型切到 8 卡（TP=8） | 讀入階段（prefill）：每步 512、2048、8192 個 token（小模型 512、2000）；生成階段（decode）：批次 1、8、32、128 |
| 訓練 | torchtitan 0.4.0（預設設定，不開 compile 與 async TP） | 中型：Llama-3 8B 架構；小型：Llama-3.2 1B 架構；隨機初始化 | TP=8；TP=4 × FSDP=2；TP=2 × FSDP=4 | 序列長度 2048；總批次固定為 8 條序列（每張卡的批次隨資料平行份數調整） |

- **建置時的設計修正（量測前）**：
  - 讀入階段原本設計「輸入長度 × 批次」，但 vLLM 會依請求抵達時間拆批（同時送 8 個請求，第一步常只有 1 個），所以改成每次 1 個請求、以「每步處理的 token 數」為變因，分析時依每步實際的 token 數分組
  - 小模型最長只支援 2048 個 token，所以讀入階段用 512 與 2000
  - profiler 會拖慢 CPU（小模型生成每步 2.0 ms → 2.9 ms），所以「端到端每步時間」改用沒開 profiler 的量測：生成用「全長 − 半長」相減；讀入用 vLLM 自己記錄的每步時間。計算與傳輸時間仍取自 profiler 的 GPU timeline（GPU 端幾乎不受影響）
  - 通訊 kernel 的時間包含「等其他 GPU 到齊」：同一個通訊操作在 8 張卡中最短的那次視為真正的傳輸，其餘算等待
- 兩個框架都用 PyTorch 2.14.0；它們各自帶的 NCCL 版本會記錄下來（可能和 nccl-tests 用的系統 NCCL 2.32.3 不同）
- 訓練用隨機權重：通訊的模式與大小只取決於模型架構，不取決於權重值

## 預期（量測前寫，量測後不改）

以下是依計算量與 M0 頻寬粗估的「沒藏住的通訊」占端到端時間比例：

| 情境 | 預期比例 | 粗估依據 |
|---|---|---|
| 推論 32B，生成，批次 1 | 10–30% | 每層 2 次約 10 KB 的 all-reduce（延遲主導），權重讀取約 5 ms／token |
| 推論 32B，讀入，2048 × 8 | 15–35% | 每次 all-reduce 約 168 MB，128 次 |
| 推論 1.1B，生成 | 20–45% | 計算很少，通訊延遲占比被放大 |
| 訓練 8B，TP=8 | 20–35% | 每層前向後向約 4 次 134 MB 的集合通訊 |
| 訓練 8B，TP=4 × FSDP=2 | 10–25% | 張量平行的通訊變少，FSDP 的通訊大多被藏住 |
| 訓練 8B，TP=2 × FSDP=4 | 5–20% | 同上 |
| 訓練 1B | 比 8B 高 | 計算少，比例被放大 |

- （設計修正後的對應，量測前補記）「讀入 2048 × 8」的預期改對應到「每步 8192 個 token」：同一量級（每次 all-reduce 約 84 MB）
- 推論的通訊幾乎不重疊（每層必須等 all-reduce 完才能往下算），所以「重疊」區塊預期接近 0
- 訓練的 FSDP 通訊預期大多被藏住；張量平行的通訊大多沒藏住
- **什麼結果會推翻預期**：某個情境的比例落在預期區間外超過 10 個百分點；或推論出現明顯的重疊
