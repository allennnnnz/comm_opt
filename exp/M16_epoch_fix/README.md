# M16_epoch_fix

- **狀態**：完成（run `20261104_104214`）；判準結果「修好但變慢」，待討論
- **核准**：2026-11-04（D033，使用者：「修漏洞」）
- **類型**：正確性測試＋速度回歸檢查（3 次獨立 launch）

## 白話結論

1. **漏洞確認存在，而且已經修好。** 舊版在交錯測試的第 3 次呼叫就卡住（120 秒後被強制結束）；新版 eager 與 CUDA graph 兩種方式各 60 次交錯呼叫全部正確，包含 1、3、13 個 token（少於 8、不是 8 的倍數）。
2. **但新版這次量到比 M15 慢 9–25%**，16 人時對 vLLM 的倍數掉到 1.24–1.27（低於 1.3）。依事先定的標準：**修好但變慢，停下來討論**。
3. **變慢有一部分不是新版造成的**：完全沒改過的 vLLM 這次也比 M15 慢 3–13%，代表這次量測時機器整體比較慢。新版比 vLLM 多慢的部分約 5–12%，推測來自每個 block 結束時多做的一次記憶體同步（等跨卡寫入完成），但還沒驗證。
4. **下一步建議**：拿掉這個可能不必要的同步，並在同一次量測裡同時跑 M15 舊版、M16 新版、去掉同步的版本，排除機器狀態的影響。


## 問題

M14／M15 原型的 epoch（回合編號，也是 LL128 flag 的值與接收區單雙數）由**每個 block 各自計數**。實際使用時，vLLM 會為不同批次大小錄不同的 CUDA graph，若它們用不同的 block 數，各 block 的計數就會分歧：送資料的 block 和收資料的 block 用不同的 epoch → 收的一方等不到相符的 flag（卡住），或讀到另一半接收區（拿錯資料）。M14／M15 每個設定都重設計數器，所以沒有踩到。

## 修法（`fused_ar_norm.cu`，由 M15 版本修改）

- 每張 GPU 只有**一個全域 epoch**（device memory）。每個 block 開始時讀它；每個 block 結束時把「完成計數」加 1，最後一個完成的 block 把完成計數歸零並把 epoch 加 1（`__threadfence` 確保順序）。下一次 kernel（同一 stream 依序執行）就讀到新的 epoch
- 因為只有在所有 block 都完成之後才遞增，所有 block 一定讀到同一個 epoch，和 block 數無關
- start barrier 的 flag 仍依 block 編號分格，但比較的是「全域 epoch 是否相等」，所以不同呼叫使用不同 block 數也一致（所有 rank 的呼叫順序相同，TP 一定成立）
- 其他（pull reduce-scatter、RMSNorm、LL128 push all-gather）不變

## 測試設計

**交錯測試**（`test_interleave.py`，8 個 rank）：一連串呼叫，交替使用不同 block 數（16／108／32／64）與不同 token 數（1、3、8、13、40、64、128，包含 < 8 與非 8 的倍數），每次呼叫都對照 fp32 參考值（輸出全部列、residual 自己的列；≤ 2^-5 算正確）。分兩種方式各跑一次：

- eager：直接依序呼叫 60 次
- graph：每種（token 數, block 數）組合各錄一個 CUDA graph（各含 1 次呼叫），依隨機順序交錯重播 60 次，每次重播後檢查

另外用**舊版（M15）kernel** 跑同一個 eager 交錯測試，限時 120 秒，預期失敗（卡住被逾時中止，或結果錯誤），證明漏洞真實存在。

**速度回歸**：照 M15 的測試程式（`bench_proto.py`，CUDA graph K=20 × R=20），新版 `P_ours`（block 數 16／32／64／108）與 `U_vllm`，fp16 與 bf16、hidden 5120，3 次獨立 launch。

## 預期（量測前寫，量測後不改）

- **P1**：舊版在交錯測試中失敗（逾時或結果錯誤）
- **P2**：新版在 eager 與 graph 交錯測試中，所有呼叫都正確、沒有逾時（包含 token 數 1、3、13 這些 < 8 或非 8 倍數的情況）
- **P3**：新版每個大小的最佳時間與 M15 同設定相差 ≤ 5%（中位數），且對 `U_vllm` 的倍數在 160K／320K／640K 仍 ≥ 1.3

## 結論

| 預期 | 結果 | 判定 |
|---|---|---|
| P1：舊版在交錯測試中失敗 | 逾時（第 3 次呼叫後卡住） | 符合 |
| P2：新版 eager 與 graph 全部正確，含 token < 8、非 8 倍數 | 120/120 正確 | 符合 |
| P3：新版與 M15 相差 ≤ 5%，且 160K／320K／640K 仍 ≥ 1.3 倍 | 慢 9–25%；160K 1.27（fp16）／1.24（bf16） | **不符** |

- **判準結果：修好但變慢 → 停下來討論**
- **限制與解讀**：
  - 跨 run 比較：vLLM（程式未改）本次也慢 3–13%，機器狀態在兩次 run 之間不同（可能與前一個被強制結束的舊版測試、時脈或溫度有關，未查）。新版扣掉這部分後約多慢 5–12%
  - 推測（未驗證）：新版每個 block 結束時的 `__threadfence()` 要等該 block 送出的跨卡寫入完成，增加了尾端延遲。這個 fence 可能不必要：epoch 在 kernel 開頭就被讀出並用在 start barrier，讀取早在遞增之前完成；下一個 kernel 依 stream 順序執行，自然看得到新 epoch
- token 數 < 8 與非 8 倍數在功能上可以運作（本測試確認正確），速度未量
