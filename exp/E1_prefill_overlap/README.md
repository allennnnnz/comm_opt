## 問題

在 8 卡 H100／H200 單機上，72B 模型 TP=8 推論的預填階段：
1. 卡間加總到底佔多少時間；
2. 讓加總和計算同時跑時，兩邊各被拖慢多少，拖慢程度是否隨資料大小與通訊方式改變；
3. 最簡單的重疊做法，能吃到理論上限（完全沒有通訊）的多少。

## 為什麼要做

- M25 量到預填步 all-reduce 佔 kernel 時間 30–35%，與計算依序執行（`exp/M25_topic_survey/README.md` 末節）。但那是附帶抓到的 1–2 步、單次啟動，要正式量。
- 文獻（`docs/reports/R08_A_papers.md`）：
  - Ladder-residual 在 8×H100、TP8、批次 1 的預填，上限 30.54%，實得 5.78%（Table 2，Opus 已核對全文）。
  - TokenWeave 在 8×H100 預填單步 1.16–1.28×。
  - 沒有論文在 Hopper 8 卡推論 TP 上量過雙向拖慢，也沒有以 vLLM 目前的 all-reduce 路徑為基準。
- vLLM 0.32.0 沒有任何預填 TP 重疊功能（`docs/reports/R08_B_code_env.md`；Opus 已核對 `compilation/passes/`）。
- vLLM 0.32.0 在 Hopper TP8 依大小換 all-reduce 實作（`distributed/device_communicators/all_reduce_utils.py:31-64`、`symm_mem.py:125`）：
  - custom ≤256 KB
  - symm_mem（multimem）≤64 MB
  - 更大走 NCCL
  - 以 hidden 8192、bf16（每 token 16 KB）換算：≤4096 token 走 symm_mem，>4096 token 走 NCCL。
- 本實驗決定「預填 TP 重疊、干擾感知、依大小調整」這個題目是否成立（判讀規則見下）。

## 預期（量測前寫，量測後不改）

**A：vLLM 預填基準**

| 編號 | 預期 | 推翻條件 |
|---|---|---|
| A1 | 72B TP8 單一請求預填，輸入長度 L = 2k／4k／8k／16k，all-reduce 佔 GPU kernel 時間各在 25–38%（兩台皆是） | 任一 L 落在範圍外 |
| A2 | 預填 wall time（TTFT 扣排程）與 kernel 時間總和差 ≤10%（依序執行、GPU 幾乎不閒） | 差 >10% |

**B：真實形狀的雙向拖慢（運算子層級）**

一個 chunk 的 all-reduce 和下一個 chunk 的計算同時跑。

| 編號 | 預期 | 推翻條件 |
|---|---|---|
| B1 | NCCL 預設設定下，通訊被拖慢 ≥30% 的格子佔一半以上；計算被拖慢 5–30% | 通訊慢 ≥30% 的格子少於一半，或計算拖慢中位數不在 5–30% |
| B2 | 限制 NCCL 運算單元（`NCCL_MAX_CTAS=8`）使計算拖慢降到預設的一半以下，但 T ≥ 4096 時通訊單獨時間變慢 ≥20% | 任一半不成立 |
| B3 | 「完成時間最短的通訊方式」隨 T 改變：20 格（4 種 T × 5 種計算）中至少 3 格，最佳方式與「全部用同一種最佳方式」差 ≥5% | 少於 3 格 |
| B4 | 重疊效率（較短那一方被藏掉的比例）跨格中位數 40–80% | 中位數在範圍外 |

**C：一層 transformer 的簡單重疊原型**

| 編號 | 預期 | 推翻條件 |
|---|---|---|
| C1 | 去掉 all-reduce 的版本（上限）比依序版本快 25–35%（對應 A1） | 範圍外 |
| C2 | 簡單切塊重疊（k=2 或 4 取較好者，NCCL 預設）在每個 L 只吃到上限的 20–60% | 任一 L 吃到 >60% 或 <20% |
| C3 | 每個 L 換用 B 部分最好的通訊方式後，吃到的比例比預設多 ≥10 個百分點，至少 2 個 L 成立 | 少於 2 個 L |

### 判讀規則（決定題目用；寫於量測前）

- **題目核心成立**：A1 在兩台都有 ≥3 個 L 的比例 ≥25%，**且** C2 在 ≥3 個 L 吃到 ≤60%（還剩 ≥40% 的上限空間）。
- **「依大小調整」有依據**：B3 **且** C3 都成立。不成立時，題目改為找一個固定的較佳做法，不做自動調整。
- **題目變弱**：C2 在所有 L 都吃到 >80%（簡單重疊已經夠好，剩下的只是工程）。
- **題目不成立**：A1 在兩台都 <20%。
- 以上任一情況都回報使用者決定，不自行改題。

## 設定

**A：vLLM 預填基準**

- vLLM 0.32.0、graph 模式、FlashInfer 關閉。設定同 M25 B2（`exp/M25_topic_survey/vllm_bench.py`）。
- 模型：Qwen2.5-72B 結構、dummy 權重、TP=8。
- 單一請求，輸入 L ∈ {2048, 4096, 8192, 16384}，輸出 1 token。`max_num_batched_tokens` ≥ L，使預填為一步。
- 每個 L：3 次引擎啟動 × 每次 10 次請求（前 2 次暖機丟棄）。
- 每次啟動以 torch profiler 抓 rank 0 的 3 次請求，另記錄每個 L 實際用的 all-reduce kernel。

**B：運算子層級雙向拖慢**（torchrun 8 卡，擴充 `exp/M25_topic_survey/overlap_bench.py`）

- **T**（chunk token 數）∈ {1024, 2048, 4096, 8192}。all-reduce 大小 = T × 8192 × 2 B = 16／32／64／128 MB。
- **計算**（每卡形狀，72B TP8；M = T）：
  - QKV GEMM：N=1280，K=8192
  - o_proj：N=8192，K=1024
  - gate_up：N=7392，K=8192
  - down：N=8192，K=3696
  - 因果注意力（SDPA，每卡 8 個 Q 頭、1 個 KV 頭、head 128、長度 T）
- **通訊方式**（各在獨立程序設定）：
  - NCCL 預設
  - NCCL 強制 NVLS
  - NCCL Ring＋LL128
  - NCCL Ring＋Simple
  - NCCL 預設＋`NCCL_MAX_CTAS=8`
  - NCCL 預設＋`NCCL_MAX_CTAS=16`
  - torch symm_mem multimem all-reduce（vLLM ≤64 MB 用的那條；只跑 T ≤ 4096）
- **量測**：通訊單獨、計算單獨、兩者同時啟動（兩條 stream）。記錄通訊拖慢、計算拖慢、完成時間、重疊效率。每格暖機 10 次、計時 50 次。

**C：一層 transformer 原型**（torchrun 8 卡，新程式）

- 層的組成：RMSNorm → QKV → 注意力 → o_proj → all-reduce → RMSNorm → gate_up → SiLU×mul → down → all-reduce，連續 8 層。
- L ∈ {2048, 4096, 8192, 16384}。
- 版本：
  - (C0) 依序：同 vLLM，all-reduce 不和計算重疊
  - (C1) 去掉 all-reduce：上限
  - (C2) 把 token 切成 k ∈ {2, 4} 塊，第 i 塊的 all-reduce 在通訊 stream 上，和第 i+1 塊的計算重疊
- C2 的通訊方式：NCCL 預設，加上 B 部分完成時間最好的兩種。
- C2 必須和 C0 的數值結果一致（容差 bf16 1e-2），否則該格作廢。
- **Opus 補充（2026-11-25 21:50，量測前，依驗證 500244）**：原容差（對 C0 相對誤差 ≤1e-2）在冒煙驗證全部超標：k=2 為 1.07–1.10%，k=4 為 1.31–1.36%。但重疊版和「同樣切 k 塊、依序執行」的版本誤差是 0.0；單層誤差 0.3–0.4%，約等於 bf16 的捨入；三種通訊方式數字相同。判斷為切塊改變 GEMM／注意力的捨入順序後，經 8 層累積的結果，不是重疊程式錯誤。有效條件改為：
  - (a) 對同 k 依序版本 ≤1e-4，用來檢查重疊程式正確；
  - (b) 對 C0 ≤3e-2，作為合理性上限。
  - 分析時用 `analyze.py --c-valid seq`，(b) 由 Opus 逐格人工確認。

**共通條件**

- **GPU**：H100 整台（排除 hgpn01）與 H200 整台各一次。開頭先做 B0 溫度檢查，不合格就中止（沿用 `exp/M25_topic_survey/thermal_check.py`）。全程記錄 GPU 時脈、溫度和同節點工作（D054）。
- **工具與版本**：vLLM 0.32.0、torch 2.13.0、NCCL 2.29.7（同 M25 venv）。
- **統計方式**：
  - B、C 每次迭代取 8 卡中最慢者（R7），每格 3 次獨立啟動。
  - 報中位數和 95% 信賴區間：迭代合併後 bootstrap，另列 3 次啟動各自的中位數，檢查一致性。
  - 依 knowledge.md 第七節，目標是中位數 99% 信賴區間在 ±5% 內；做不到就報實際區間。
  - 拖慢以比值表示，不跨格平均；中位數只用在 B4。
- **理論上限**（R8）：
  - 上限是 C1（沒有通訊）。
  - all-reduce 單獨時間對照 M25 C1／C2 的頻寬（Ring 約 360 GB/s；NVLS 約為 Ring 的 1.22–1.30 倍）。

- **Opus 補充（同上，實作差異，量測前記錄）**：
  - B 段每次計時迭代連續做 R = 8192/T 對（通訊與計算各 R 次），避免單一小 kernel 的計時雜訊。拖慢與重疊效率是比值，不受影響。
  - C 段沒有 RoPE；注意力用 SDPA＋`causal_lower_right`，K/V 展開成 8 頭。C0 因此不等於 vLLM 的 kernel 組合，只用於 C0／C1／C2 之間的相對比較。

**預估時間**：每台約 1 小時 45 分（B0 5 分、A 約 45 分、B 約 35 分、C 約 15 分），申請 3 小時。
- **Opus 補充（2026-11-25 21:00，量測前）**：使用者要求不要因時間不夠而跳過項目（M25 H100 曾因此跳過 7 項）。主工作改申請 5 小時，區塊上限改為 B0 10 分、A 90 分、B 90 分、C 60 分。只改時間，量測設定與預期不變。H100 走 `normal`（上限 48 小時），H200 走 `normal2`；只有 2 卡冒煙驗證用 `dev`。

**實作**：核准後，Opus 寫規格書 S09，由 Sonnet 寫腳本。先在 `dev` 用 2 卡做冒煙驗證，再送兩台主工作。
