# E2_overlap_cause：大塊計算時，通訊是在等資源，還是同時執行卻互相拖慢？

- **狀態**：提案，待使用者核准；未實作、未送出任何工作
- **核准**：無。本卡本身與後續冒煙驗證、正式量測皆須先獲核准
- **類型**：機制探索；同一台 H200、3 次獨立啟動。可判讀本機代表格，不外推整個模型或其他機型

## 白話結論

目前沒有實驗結果。以下是提案要回答的事：

1. 先看通訊何時真的開始，分清楚「還沒輪到它」與「已經在跑，卻跑得很慢」。
2. 分別試通訊先送出、提高通訊優先權，以及讓矩陣計算少用一些運算資源，檢查等待是否減少。
3. 即使通訊提早開始，也要看全部工作是否更快完成；若只是把拖慢轉到計算端，就不算改善。
4. 時間線若顯示兩者早已同時執行，就不支持原先的單純排不上猜想；再檢查記憶體負載，但證據不足時保留未定。

## 問題

E1 在大塊輸入下幾乎沒有重疊，主因是否為矩陣計算佔用運算資源，使通訊 kernel 延後開始？還是兩者已重疊，但受共同資源限制而變慢？

### 依據與邊界

- E1 H200（500259，hgpn46）觀察：T=8192 的 gate_up 計算單獨約 1.27 ms、通訊約 0.58 ms，同時提交後完成約 1.82 ms。這只能顯示接近依序耗時，**不能證明通訊沒有開始**。
- 證據：`exp/E1_prefill_overlap/README.md`「結論」；原始數據 `results/E1_prefill_overlap/20261125_224619_job500259_h200/b/default_l{1,2,3}.jsonl`。
- E1 的 `Runner.conc()` 先提交計算，再提交通訊；兩條 stream 等同一個事件。`ProcessGroupNCCL` 實際使用自己的 stream，不能只看 Python 外層 stream。
- 本卡不改 E1 的預期、判定或原始數據，不改研究問題與 claims；不做端到端加速宣稱。

## 預期（提案；核准後、量測前固定，跑完不改）

| 編號 | 預期 | 推翻或無法判定的條件 |

| P4：小格對照 | T=1024 的兩格，基準時間交集比例高於同運算的大格 | 未重現或差異不明確：推翻／未定，據實報告 |

### 判讀規則

- **支持排程資源限制**：P1 成立，排除 CPU 晚送、stream/event 依賴和其他 rank 晚到；P2 或有效的 P3 至少一項使等待減少。只能寫「支持」，時間線本身不證明每個運算單元都滿載。
- **不支持單純排不上**：大格通訊很早開始並有明顯交集，主要增加的是 kernel 本身執行時間。不能把等待其他 rank 的通訊 kernel 當成有效資料傳輸。
- **記憶體頻寬爭用候選**：上一項成立，且重疊時記憶體吞吐接近可觀察上限、兩方 kernel 都變長。硬體計數器只提供旁證；沒有控制記憶體流量的介入，不能宣稱已證明它是主因。
- **混合／未定**：不同 rank、運算或啟動結果不同；工具無法提供所需證據；提示設定未生效。不可硬選唯一原因；若需新增實驗，另提卡取得核准。

## 設定

### 固定條件與代表格

- **GPU**：一台 H200、8 卡（`normal2`，盡可能 hgpn46，若不同節點明列）。先驗證 E1 大格現象有重現，再解讀原因；不追加 H100 工作。
- **形狀**：沿用 E1 bf16、TP8，T ∈ {1024,8192}；gate_up 的 (K,N)=(8192,7392)，down=(3696,8192)。通訊資料 T×8192×2 B，即 16／128 MiB。
- 選這四格是因大格 gate_up／down 重疊很差，T=1024 作小格對照；不代表其他運算。保留 E1 每次迭代 R=8192/T 對的設定，時間線逐對對應，另列整批結果。
- **通訊**：僅 NCCL 預設，不掃演算法或 CTA 數；記錄實際 kernel 與環境變數。
- **環境**：沿用 E1 vLLM venv 的 torch／NCCL 與 CUDA 模組；記錄實際版本、driver、GPU 拓樸、腳本 commit、seed、啟動順序。

### 一次只改一項

| 版本 | 與對照相比唯一改動 | 範圍 |
|---|---|---|
| V0 | E1 原提交順序、預設優先權 | 四格；另量計算單獨、通訊單獨、依序執行 |
| V1 | 改為先提交通訊，再提交計算；仍由同一事件釋放，沒有等待通訊完成 | 四格；其餘同 V0 |
| V2 | 原提交順序，只將 NCCL process group 設成高優先權 stream | 四格；其餘同 V0 |
| V3 | 矩陣計算資源目標設為 S、S−16、S−32（S 為實測運算單元總數） | 僅兩個大格；同一 cuBLAS/cuBLASLt 後端，S 為自身對照 |

- V1 是提交順序干預，不保證 GPU 一定先執行通訊；必須以時間線確認。
- V2 用 `ProcessGroupNCCL.Options.is_high_priority_stream`，記錄實際 NCCL stream；只設定 `torch.cuda.Stream(priority=...)` 不算完成。優先權不能搶走已在執行的工作，無效也可能符合排程限制。
- V3 優先沿用實際 GEMM 後端，查 `cublasSetSmCountTarget` 或 `CUBLASLT_MATMUL_DESC_SM_COUNT_TARGET`；它們是演算法選擇提示，**不是硬性資源隔離**。保留呼叫回傳值、讀回值（若有）、kernel/grid/block/資源配置；只讀回成功不足以證明生效。
- 若 V3 必須以獨立 cuBLASLt wrapper 取代 `torch.mm`，先保留其目標 0 預設、S 全量目標兩個對照，驗證 bf16 輸出相對 L2 誤差 ≤1e-2、單獨時間與 V0 差 ≤10%；不符就列後端差異，P3 不作原 E1 因果判定。降低目標時單獨時間與正確性都須重測。
- V3 若不支援或無可驗證效果，記為「不可判定」；不改用其他演算法、切塊或資源隔離技術補跑。

### 時間線、量測與統計

1. 同一張已核准的整台工作先做環境／工具預檢與 B0 溫度檢查。GPU 有其他工作、B0 不過、必要追蹤失敗就停止，不自動重送。開始／結束留 `cotenants_summary.txt`。
2. **不錄影的效能量測**：3 次獨立 torchrun 啟動；每格暖機 10、計時 50 次。固定 seed 並將格子／版本順序隨機化，單獨與重疊對照成組交錯；初始化、配置、正確性檢查不進計時。
3. **另錄時間線**：同樣 3 次獨立啟動，各格暖機後取 10 次代表迭代；收 8 個 rank 的 CUDA API、kernel、NVTX、event 依賴。NVTX 標格子、版本、迭代及 rank；追到 NCCL 內部 stream，不只看外層 CUDA event。
4. 對每對計算／通訊，記錄主機提交時刻、共同開始事件／前置工作解除時刻、GPU 開始／結束、計算與通訊的時間交集。等待從「提交與已知依賴均就緒」算到 kernel 開始；分別列總排隊延遲，不能把已知依賴或 CPU 未送出的時間算成資源等待。若就緒時刻無法可靠取得，該項標未定。
5. 各 rank 各自分析排程與重疊；跨卡時間比較須確認時鐘校準。檢查有無任一 rank 晚到，通訊是否已啟動卻在等其他卡，不只看 rank 0。
6. 對同一迭代先跨 8 卡取最大完成時間，再算總完成時間的中位數、95%／99% bootstrap CI、各次啟動中位數；重疊比例與等待則逐 rank 列。以啟動為群組重抽樣，不把 150 次迭代當成 150 次獨立啟動；3 群樣本少，區間僅供探索。報實際 99% CI 是否達 ±5%，不足不稱定論、不為湊門檻自動增跑。
7. 錄製與未錄製的完成時間差 >10% 時標出追蹤干擾；不能用受干擾的時間線直接解釋未錄製效能。改善的百分比必須附絕對時間與計算單獨的代價。
8. 同一次預檢確認 `nsys` 是否支援並有權取得 SM active、DRAM throughput、NVLink 等 GPU metrics；有則另錄短段作旁證，避免同時啟動多個全卡 metrics 收集器。無權不提權、不換量法，保留時間線、記憶體原因維持未定。取樣未覆蓋足夠的 kernel 活躍區間時也不判讀。

**理論上限**：每格以 max(計算單獨時間, 通訊單獨時間) 為完全重疊下限，兩者和為依序參考；只用相同版本／後端的單獨時間作對照。不把改慢計算後看似變高的重疊比例當效能改善。

**預估資源**：一台 8 卡，執行約 30–60 分鐘，申請 90 分鐘（含預檢與追蹤餘裕）。先列出完整格子清單，不因時間不夠悄悄跳過；不足則標未完成並回報，不自行補送。
